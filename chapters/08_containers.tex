\chapter{Containers}

\section{Motivation for lightweight virtualization}

Computer virtualization provides a set of desirable system properties, including \emph{scalability} (the ability to increase or decrease capacity by adding or removing execution units), \emph{elasticity} (the ability to adapt resource allocation to varying demand), and \emph{isolation} (the containment of faults, interference, and security-relevant effects within a defined boundary). Traditional virtualization techniques achieve these goals by virtualizing hardware and running guest operating systems on top of a hypervisor. While effective, full machine virtualization introduces overheads associated with device emulation, additional kernel instances, and the management of virtual hardware.

\begin{notebox}
	\textbf{Why another form of virtualization?} Traditional virtualization means virtualizing full computers, from the hardware to the applications themselves. With hypervisors and the techniques seen so far (full, para and hardware-assisted virtualization), a physical machine can host additional VMs, which cloud providers use to deliver their services: for example, they can constantly create new VMs, flexibly replicated on the same physical infrastructure, whenever the workload of a customer increases, so that more requests are served at the same time by a higher number of machines. Traditional virtualization is still widely used (everybody has VirtualBox or VMware on a personal computer, to test other operating systems or to do exercises for courses), so the question is why an alternative is needed. The answer is that we need a virtualization that is \emph{lighter} than the traditional one.

\medskip
\textbf{Example.} Consider a very light application that consumes only 100~MB of memory and few CPU cycles, and that a cloud provider wants to offer to its consumers as software as a service. The provider would like to create virtual environments each containing a single instantiated process of that application, so that every consumer interacts with a perfectly isolated process, which is not affected by the others because they live in different environments. If these environments are traditional VMs, then, even if each application uses only 100~MB, each VM also needs the virtualized hardware and a guest operating system. Just to provide isolation in this multi-tenant scenario the provider spends physical resources and CPU time on management overhead due to virtualization.
\end{notebox}

Lightweight virtualization aims to preserve the operational benefits of virtualization while reducing resource consumption and deployment latency. It is particularly appropriate when the overhead of classical virtual machines is unacceptable, or when the primary requirement is a rapidly deployable, migratable, and disposable isolated environment with minimal performance impact. Lightweight approaches emphasize fast creation and teardown, high density (many isolated environments per host), and integration with native process scheduling and resource management.

The idea is therefore to get rid of this overhead with a technique that consumes fewer resources, so that multiple virtual environments (which will no longer be called virtual machines) can be instantiated using less resources and less time than traditional VMs. The goals are three:

\begin{enumerate}
\item consume \textbf{fewer resources} to deploy virtual environments;
\item be \textbf{faster} in deploying, modifying and possibly stopping them;
\item keep the environments as \textbf{isolated} from each other as possible. Without isolation we would go back to the original situation in which all processes run on the same machine, compete with each other for the resources and may interfere with each other, with problems also related to privacy.
\end{enumerate}

\subsection{Operating system-level and application-level virtualization}

Lightweight virtualization is typically implemented as \emph{operating system-level virtualization} or \emph{application-level virtualization}. In operating system-level virtualization, isolation boundaries are constructed by the host kernel itself. The host kernel provides a set of mechanisms that make a group of processes perceive a restricted and customized view of system resources, while still executing as ordinary processes from the host perspective. In this setting, the role played by a hypervisor in full virtualization is largely replaced by kernel subsystems and user-space tooling.

Application-level virtualization focuses on packaging and isolating an application and its dependencies in a way that can be executed reliably across environments, often relying on the same kernel mechanisms as operating system-level virtualization. In both cases, the central idea is to avoid running multiple kernels and to avoid hardware emulation.

Operating system-level virtualization means that a new operating system level is no longer created over the host operating system: an existing operating system is taken and made to work as the ``hypervisor'' of the new lightweight virtual environments. This may look similar to a type 1 hypervisor, where the host OS is fully replaced by the hypervisor, but here things are even more different, because there is no dedicated hypervisor: normal operating systems are used, and some of their specific features are exploited to provide isolation, agility and flexibility in the management of virtual environments.

The operating system most commonly used is Linux, with all its variants, because it natively offers \emph{cgroups} and \emph{namespaces}, the building blocks of these virtual environments. The technique was so successful that other operating systems followed and introduced analogous features (Windows, for example, has alternative ones), so what is studied for Linux can be replicated in other ways. In this course the focus is on Linux.

These virtual environments have had different names over the years: first \textbf{jails} (in the FreeBSD operating system), then \textbf{virtual private servers} and nowadays \textbf{containers}, the name used from now on. A container is a \emph{partial} virtual computer: it does not virtualize everything, and its goal is to give to some processes (instantiated applications) guarantees similar to those of processes running in traditional VMs; not all of them, but as many as possible. As a consequence the concept of guest operating system is lost: containers simply live on a normal host operating system.

\subsection{Controllable properties}

A lightweight virtual environment can be configured to control, isolate, and account for multiple classes of resources:

\begin{itemize}
\item \textbf{CPU and disk quotas}: upper bounds on CPU time allocation and constraints on disk throughput or usage.
\item \textbf{I/O rate and memory limits}: caps on memory usage and limits on I/O bandwidth or operations.
\item \textbf{Network isolation}: separation of network stacks, addresses, routing tables, and filtering rules.
\item \textbf{File system isolation}: separation of mount points and directory trees, yielding distinct file system views.
\item \textbf{Root privilege isolation}: restriction of privileged operations even when a process appears to be a superuser within an isolated environment.
\end{itemize}

These properties are realized primarily through Linux \emph{control groups} (cgroups) and \emph{namespaces}. Together they provide the building blocks for container technologies.

The two mechanisms serve different purposes. \textbf{Cgroups} are used for resource \emph{usage limitation}: a group of processes is bound to limits in the use of physical resources such as CPU, memory and I/O devices. \textbf{Namespaces} are used for resource \emph{visibility}: groups of processes are made able to see only part of the existing resources, and in many cases to see different things, for example two completely different networking stacks, so that they interact with external networks thinking to be different entities, something that is not true from the physical point of view, because the physical machine is one and the separation is only simulated. In the list above, the first two properties (quotas, I/O and memory limits) concern the control of resource usage, while the last three (network, file system and root privilege isolation) concern visibility.

\begin{notebox}
	\textbf{An analogy.} Think of a building with many apartments. Each apartment can be assigned a maximum consumption of water or electricity per day: this is the equivalent of cgroups. Namespaces are more like the walls between the apartments: each family has only a partial view of the whole building, even though the physical building is shared. At the same time, this isolation is not very strong, because all the families live in the same building and can easily interact just by opening the doors of their apartments: we are not in a situation of strong isolation like the one of traditional virtualization.
\end{notebox}

The first principle of lightweight virtualization is thus to take a group of processes and manage them so that they think to be isolated containers, while they actually reside on the same machine. Besides CPU and disk quotas, the properties that can be managed include the rate of interaction with I/O devices, memory limits, network isolation, file system isolation (for example each group may have its own separate \texttt{/etc} folder) and the privileges of root that the processes may have.

\section{Linux control groups}

A \emph{control group} (cgroup) is a collection of processes bound by a criterion and associated with a set of parameters or limits. The kernel enforces these parameters by attaching resource controllers to a cgroup and applying controller-specific policies to all member processes.

Without cgroups, each process is an entity by itself: at most an operating system can give different priorities or limits to each single process (Linux, for example, can choose through its scheduling algorithms to give more priority to one process than to another because it was started by a certain user), but it cannot give limits that are related to \emph{multiple processes at the same time}. This is exactly what is needed for containers, where several processes may run in the same virtual environment: to separate and control them with respect to the processes of other groups, limits shared by multiple processes are needed, and the group must fully respect them. For example, if a group is allowed at most 8~GB of memory, the processes of the group can never request more than 8~GB overall: one process may use all 8~GB and the others be unable to work, or the memory may be shared (for instance 2~GB, 2~GB and 4~GB). What matters is that the limit is on the \emph{group}, and the sum of the resources used by its processes cannot exceed it.

This is not so different from what happens with traditional virtual machines: each VM is assigned resources defined by the virtual hardware profile, which are then mapped to real hardware. With type 1 hypervisors resources can be over-allocated, hoping that they are not fully used, but if they are, one ends up in a similar situation in which the resources are exhausted. Likewise, a number of CPU cycles can be reserved to each group, with different values so that some groups are prioritized over others, as a hypervisor can give higher priority to some VMs through the configuration parameters of the VMM software embedded in it.

\subsection{Resource accounting and limiting model}

Let $G$ denote a cgroup and let $P(G)$ denote the set of processes that belong to $G$. For a resource class $R$ (for example CPU time, memory, or block I/O), define a usage function $u_R(p, t)$ for process $p$ over an interval ending at time $t$. A controller provides:

\begin{itemize}
\item an \emph{accounting function} that aggregates usage for the group, such as
\end{itemize}

\[ U_R(G, t) = \sum_{p \in P(G)} u_R(p, t), \]

\begin{itemize}
\item and a \emph{policy} that constrains usage, such as an upper bound $U_R(G, t) \le L_R(G)$ or a proportional share policy.
\end{itemize}

Controllers vary by resource class. For memory, a limit typically constrains total resident memory and may include file system cache. For CPU, allocation is often expressed as a share or quota within a period. For block I/O and network bandwidth, policies may implement weights, ceilings, or rate limits.

\subsection{Core capabilities}

Linux cgroups provide four families of capabilities.

\subsubsection*{Resource limiting}
\addcontentsline{toc}{subsubsection}{Resource limiting}

Resource limiting constrains a group so that its total consumption does not exceed configured limits. Typical examples include a memory limit that caps the total amount of memory that processes in the group can use, and I/O constraints that restrict throughput.

For memory, the kernel may trigger reclaim or invoke the out-of-memory mechanism for the group when the limit is exceeded. The exact behavior depends on the controller version and configuration, but the core principle is that the limit is enforced at the group boundary rather than per process.

So the main goal of control groups is to define a maximum limit on memory, CPU and disk that cannot be exceeded by the group of processes to which it refers.

\subsubsection*{Prioritization}
\addcontentsline{toc}{subsubsection}{Prioritization}

Prioritization assigns a relative share of a resource to a cgroup. If multiple groups contend for CPU time, CPU scheduling can be influenced by weights or shares associated with each group. Analogously, disk I/O and network bandwidth can be distributed using weights that determine proportional access during contention.

Prioritization is distinct from limiting. A group with higher weight does not necessarily receive a fixed amount; it receives a larger fraction under contention. When contention is absent, groups may use more resources than their shares would suggest, depending on the policy.

Prioritization is strictly related to resource limiting: when different limits are assigned to different groups of processes, each group obtains a different preference.

\subsubsection*{Accounting}
\addcontentsline{toc}{subsubsection}{Accounting}

Accounting measures resource usage of the group. These measurements support administrative goals such as chargeback and billing, as well as operational monitoring. Accounting data is typically made visible via pseudo-files in a cgroup file system hierarchy.

Accounting is especially important for cloud computing. The measurement can easily be done by the cgroup controller active in the operating system, which continuously checks how many resources are used by each group of processes, because the operating system must verify that the groups do not exceed their limits. Recall one of the basic characteristics of cloud computing: the provider should bill the consumers only for what they actually use. Having a native mechanism to monitor the resources actually used is therefore ideal: with cgroups lightweight virtualization is provided by giving limits and different priorities to groups, and the resource usage can also be checked without a dedicated software such as the hypervisor, which was needed instead to manage traditional VMs.

\subsubsection*{Control and lifecycle management}
\addcontentsline{toc}{subsubsection}{Control and lifecycle management}

Control capabilities include freezing and thawing groups of processes. Freezing suspends execution without terminating processes, enabling use cases such as check-pointing and controlled migration. Restarting and resuming can then be orchestrated by user-space tools that coordinate process state, resource configuration, and file system context.

The cgroup manager can control the life of the processes themselves. If it notices that a group of processes is behaving badly, for example because it constantly requires new resources exceeding the defined limits, it may at least temporarily freeze the group and restart it when it wants. In the extreme case it may terminate the processes, for example when one process is running out of memory and will never be able to proceed because the limit cannot be changed. This fourth capability shows that the cgroup manager can do more than setting limits: it can control the life cycle of groups of processes.

\subsection{Cgroups as an enabling mechanism for containers}

Cgroups provide the resource management foundation for operating system-level virtualization by allowing container runtimes to enforce resource constraints at container boundaries. When a container is modeled as a set of processes, placing those processes into dedicated cgroups enables per-container limits, proportional shares, and observability.

It is worth noting that the cgroup feature was \emph{not} created for virtualization. It was originally introduced to give limits and priorities to groups of processes; only afterwards did it become an ingredient of containers, because it was also suitable to provide these virtual environments.

\section{Linux namespaces}

Namespaces virtualize global system resources by wrapping each resource class in an abstraction that provides processes within a namespace an isolated instance of that resource. Processes in different namespaces can therefore observe distinct system identifiers, network configurations, file system mount points, and other kernel-managed objects.

A typical abstraction is the one related to the file system. Normally all processes active in an operating system share the same file system: if they go to the folder \texttt{/etc}, they all see the files saved there by the others and can modify them. With namespaces each process (or group of processes) may see a different file system: two processes placed in different Linux namespaces that go to the same folder \texttt{/etc} see different files, because that is not the real \texttt{/etc} but an abstraction of the original one towards separate entities. These abstractions are not applied only to file systems, but to other resources too.

\subsection{General isolation principle}

Consider a global kernel resource type $X$ (for example the network stack). A namespace mechanism creates disjoint instances $X_1, X_2, \dots$, and associates each process with exactly one instance. Kernel operations performed by a process are resolved with respect to the instance associated with that process. Isolation means that operations on $X_i$ are not visible through $X_j$ for $i \neq j$, subject to explicit inter-namespace communication mechanisms.

Namespaces can be combined. A process may simultaneously belong to a mount namespace, a network namespace, a PID namespace, and so on. This composability enables custom isolation boundaries, but it also increases management complexity.

Note that, by default, a namespace does not abstract all the resources: it abstracts one specific resource. Several namespaces can be combined to obtain abstraction with respect to multiple features (for example a PID namespace plus a network namespace, putting the same processes in both, so that they share the characteristics of both), or one can focus on a single resource at a time.

\subsection{Namespace types in Linux}

Linux implements several namespace types that collectively cover the most relevant aspects of operating system-level isolation.

\subsubsection*{Mount namespaces}
\addcontentsline{toc}{subsubsection}{Mount namespaces}

Mount namespaces isolate the set of file system mount points visible to a process. Two mount namespaces can have different mount trees and therefore different views of the directory hierarchy. This is essential for containers because it enables each container to have its own root file system and its own view of system directories such as /etc. Mount namespaces are created with the CLONE\_NEWNS flag.

Mount namespaces are not the most commonly used for virtualization, since this feature was created for other purposes, but having different file system mount points was considered quite useful.

\subsubsection*{UTS namespaces}
\addcontentsline{toc}{subsubsection}{UTS namespaces}

UTS namespaces isolate system identifiers, in particular the hostname and NIS domain name. This allows processes in different UTS namespaces to observe different hostnames, supporting the illusion that each container is a distinct host. UTS namespaces are created with the CLONE\_NEWUTS flag.

In the words of the professor, UTS namespaces provide the isolation of the OS name.

\subsubsection*{IPC namespaces}
\addcontentsline{toc}{subsubsection}{IPC namespaces}

IPC namespaces isolate interprocess communication resources such as System V IPC objects and POSIX message queues. This prevents processes in distinct namespaces from accessing shared memory segments, semaphores, and other IPC objects unless explicitly shared. IPC namespaces are created with the CLONE\_NEWIPC flag.

These are the data structures (variables, shared segments, semaphores) that are written and read by multiple processes to manage concurrency when they access the same memory, so that they do not interfere with each other.

\subsubsection*{PID namespaces}
\addcontentsline{toc}{subsubsection}{PID namespaces}

PID namespaces isolate the process identifier space and the process tree. A process can have different PIDs in different PID namespaces, and processes in a child PID namespace can observe a process tree rooted at an init-like process for that namespace. This supports the abstraction that a container has its own process tree, independent of the host. PID namespaces are created with the CLONE\_NEWPID flag.

Normally two processes cannot have the same PID, because each PID characterizes the position of a process in the hierarchy of the process tree, depending on the various forks performed by the applications. With PID namespaces, instead, two processes may both think to be the process with PID 8: they are put in separate namespaces, which make them believe to have the same PID while they are actually mapped to different real ones.

\subsubsection*{Network namespaces}
\addcontentsline{toc}{subsubsection}{Network namespaces}

Network namespaces isolate the network stack. Each network namespace has its own set of network interfaces (including virtual interfaces), IP addresses, routing tables, and firewall rules. This enables two namespaces to have independent networking configurations, even though they run on the same host.

A common configuration uses a host (or global) network namespace and one or more container network namespaces. Virtual Ethernet pairs (veth) are often used to connect a container namespace to a bridge in the host namespace. Conceptually, one endpoint of the veth pair appears as a network interface inside the container namespace, while the other endpoint appears in the host namespace. The host can then connect multiple container endpoints via a software bridge and can apply routing and filtering rules.

Each network namespace has its own complete networking stack: processes may think to interact with a different instance of the IP protocol and to send packets through a different Ethernet layer and a virtual Ethernet interface. In the typical configuration there are a root network namespace and a container network namespace, each with a loopback interface, its own \texttt{iptables} (the firewall implementation of the Linux kernel, a packet filter working on the values of the IP 5-tuple; it cannot, for example, filter by URL or domain) and its own virtual interfaces. Since the firewall is replicated, each namespace may have completely different rules and configuration, for instance a default deny action in one and a default allow action in the other.

The interaction between namespaces is easy: each one may host an application server and they communicate through the virtual interfaces. Moreover, the processes of these applications may be associated with the \emph{same transport-layer port}, because the networking stacks are completely different. The virtual interfaces can also communicate with the physical one, which communicates with the outside. If two processes use the same port, how can they be made visible outside, since an incoming packet reaching the physical interface could not be identified? The solution is an internal translation: the networking stack of the real machine maps a port made visible on the outside to the internal one, so that it can forward the packets to the virtual interface of a container or of another one. The routing process shown on the right of the figure may be in charge of this translation, because it can enrich its routing entries so as to discriminate packets coming from the outside and send them to different network namespaces. Network namespaces can therefore interact both with each other and with the outside world. (Virtual machines could do the same, but that was easier to imagine because each of them was a full computer, virtualized or physical.)

\begin{notebox}
	\textbf{Is this isolation strong?} No. With a network namespace only one resource is differentiated for different processes, while all the others stay the same: the file system, the process tree, the shared segments and semaphores are shared. Above all, it is just an abstraction: the computer in which all the processes live is the same. This is a first sign that with lightweight virtualization we will never reach the strong isolation of virtual machines, and we have to give up, at least partially, that guarantee.
\end{notebox}

Network namespaces are created with the CLONE\_NEWNET flag.

\subsubsection*{User namespaces}
\addcontentsline{toc}{subsubsection}{User namespaces}

User namespaces isolate user and group identifiers. They enable a mapping between user IDs inside a namespace and user IDs on the host. A typical use case is to allow a process to have user ID 0 (the superuser) inside the namespace while being mapped to an unprivileged user ID outside the namespace. This supports root privilege isolation by reducing the impact of privileged operations to the namespace boundary. User namespaces are created with the CLONE\_NEWUSER flag.

\subsubsection*{Cgroup namespaces}
\addcontentsline{toc}{subsubsection}{Cgroup namespaces}

Cgroup namespaces isolate the view of the cgroup virtual file system hierarchy presented to a process. A process can therefore see a virtualized cgroup path that is meaningful within the container context rather than the host-wide cgroup structure. Cgroup namespaces are created with the CLONE\_NEWCGROUP flag.

\subsubsection*{Time namespaces}
\addcontentsline{toc}{subsubsection}{Time namespaces}

More recent versions of Linux introduced an additional (eighth) namespace, the time namespace, which allows processes to see all the time-related entities, including the clock, in a separate way.

\section{From kernel building blocks to containers}

Cgroups and namespaces are general-purpose kernel mechanisms, originally developed for process isolation and resource management rather than full virtualization. When combined, they can implement a lightweight virtual environment in which a set of processes is constrained in resources and observes a restricted system view.

Once cgroups and namespaces have been presented, it is possible to evaluate to what extent they are useful for virtualization. Compared with traditional virtualization, both show native limitations.

\subsection{Limitations of raw cgroups and namespaces}

When used directly, cgroups and namespaces exhibit important limitations for large-scale and practical deployments.

\subsubsection*{Management complexity}
\addcontentsline{toc}{subsubsection}{Management complexity}

The mechanisms are highly flexible. Each namespace type and each cgroup controller can be configured independently. However, this flexibility implies that creating a coherent isolated environment requires multiple coordinated operations, such as setting up mount points, configuring user mappings, building a network topology, and assigning cgroup policies. Doing so directly often requires extensive scripting and intimate familiarity with kernel interfaces.

These features are low-level, compared with the high-level control of VMs that one has with type 2 hypervisors. Managing them is not easy at all: a human user would need a complete overview of all the processes living in the physical computer, understand how to divide them into groups, define correctly the limits of the control groups and then create the namespace abstractions. All these are low-level operations that require interacting with the command line and command-line instructions; so, even if flexible, the creation of virtual environments becomes even less user-friendly than with virtual machines.

\subsubsection*{Portability}
\addcontentsline{toc}{subsubsection}{Portability}

Full virtual machines can be packaged as images that include the guest operating system and are expected to boot on any compatible hypervisor that reproduces the virtual hardware environment. In contrast, an environment constructed from namespaces and cgroups depends on host kernel features and on host-specific configuration. Packaging an isolated application so that it can be instantiated on another server in a consistent way requires additional tooling, conventions, and image formats.

For VMs, the virtual hardware profile can be replicated from one physical computer to another as long as the hypervisor is the same. With OS-level virtualization there is no longer virtualization of the hardware and of the operating system: applications simply run in separate environments over the same OS, so one might expect portability to be easier, but it still has limitations. A group of processes cannot be moved from a Linux machine to a Windows machine, because the features are completely different. Even moving a cgroup from one Linux machine to another is not easy: the machines have different hardware, so one cannot take for granted that the same limits remain valid, as the amount of hardware may differ and the limits should be revised; the same holds for namespaces. Since cgroups and namespaces are kernel features and the Linux kernel is common, this is positive for portability, but in general portability is more related to the hardware limits.

\subsubsection*{Lack of datacenter-scale orchestration}
\addcontentsline{toc}{subsubsection}{Lack of datacenter-scale orchestration}

Cgroups and namespaces alone do not provide a control plane for placing workloads across a fleet of machines, reacting to machine failures, or coordinating networking and storage at cluster scale. Additional layers are required to manage the lifecycle of isolated environments, to provide service discovery, and to implement self-healing behaviors.

A cloud provider should, by definition, have minimal manual interaction with the infrastructure on which the delivery model is provided. With raw cgroups and namespaces user-friendliness is lost and automation is much less feasible than in the past. So, after seeing that cgroups and namespaces seem good for lightweight virtualization, one almost finds the opposite: for cloud computing they are nice but difficult to handle. The solution is to keep them but add a software layer that manages cgroups and namespaces automatically: a \textbf{userland configuration tool}. It may be called a container orchestrator or container manager, depending on the implementation; what matters is that it is a collection of tools that automate the use of control groups and namespaces.

\subsection{LXC containers}

LXC (Linux Containers, commonly pronounced \emph{lecsi}) is a container technology that assembles cgroups and namespaces into a cohesive container abstraction and provides user-space configuration tools. LXC operates on a standard Linux kernel without requiring kernel patches.

LXC containers were the first containers ever created in history. The idea of modern containers is not very different: the next lecture and the third lab activity are about Docker, which is still based on cgroups and namespaces but has a much richer userland configuration toolset, so that more capabilities and even higher user-friendliness are provided, while the concept remains the one of the original LXC container: the combination of cgroups, namespaces and software tools.

An LXC container can be understood as:

\begin{itemize}
\item a set of processes isolated by namespaces (for example mount, UTS, IPC, PID, network, and user namespaces),
\item placed into cgroups to enforce resource constraints,
\item configured via user-space tools that manage the container root file system, initialization process, and runtime parameters.
\end{itemize}

This organization turns low-level kernel primitives into a usable environment that resembles a virtual machine from the inside while remaining a set of ordinary processes from the outside.

\section{Containers as a software packaging and execution unit}

A \emph{container} is an executable unit of software in which application code is packaged together with its libraries and dependencies, using conventions that allow the unit to be run consistently across environments. Containerization relies on operating system virtualization, leveraging kernel mechanisms such as Linux namespaces and cgroups to isolate processes and control their resource access.

The dependencies and libraries packaged in a container may depend on the specific operating system, so a container cannot simply be moved from one OS to another without modification: some adaptation may be needed. For example, a Linux container uses namespaces and cgroups, whereas Windows has the equivalent \emph{silos} and \emph{job objects}, so different tools are needed to manage these different features.

\subsection{What containers do}

Containers implement the following behaviors.

\begin{itemize}
\item \textbf{Process grouping with isolation}: a container groups one or more processes that collectively implement an application component. Namespaces provide a container-local view of system resources such as the file system and the network.
\item \textbf{Resource governance}: cgroups impose constraints and shares over CPU, memory, and I/O resources for the processes belonging to the container.
\item \textbf{Host operating system sharing}: containers share the host kernel. The host schedules container processes like any other processes.
\item \textbf{Dual perspective}: from inside the container, the environment appears similar to a separate machine, with its own process tree, hostname, and network configuration. From outside, the container appears as a set of processes with associated cgroup membership and namespace associations.
\end{itemize}

The processes of a container live in the same operating system as the host and may therefore compete with the normal processes that do not belong to these groups, that is, the processes of the normal operating system (the so-called \emph{root namespace}, which characterizes the standard machine). Containers may look like VMs because they have some controls, but they are normal processes: there is no real isolation in the sense of VMs.

\subsection{What containers do not do}

Containers do not provide certain properties commonly associated with full virtual machines.

\begin{itemize}
\item \textbf{No hardware emulation}: containers do not emulate devices or provide a virtual hardware platform.
\item \textbf{No distinct kernels}: containers do not run different kernels or operating systems. They execute on the host kernel.
\item \textbf{Security requires configuration}: containerization does not automatically guarantee strong security isolation. Kernel attack surface is shared, and misconfiguration can lead to privilege escalation or data exposure. However, an appropriate security level can be achieved by combining namespaces, user namespaces, capability restrictions, mandatory access control, and careful image and runtime practices.
\end{itemize}

Security for containers cannot be taken for granted. This module does not discuss security, but reasoning about how to enforce it for containers is a central topic: additional boundaries must be put in place so that one container does not interfere with the others, since otherwise there is no immediate control by which this property is achieved.

\subsection{Revisiting the goals of lightweight virtualization}

The goals stated at the beginning can now be checked.

\begin{itemize}
\item \textbf{Fewer resources.} Achieved, because there is no hypervisor: lightweight virtualization is provided by native features of the OS kernel (cgroups and namespaces) plus some additional tools. The operating system is no longer virtualized, so the variables and data structures required for full hardware and system virtualization are not used.
\item \textbf{Faster deployment.} Achieved. In traditional virtualization every VM contains a guest OS, whose installation may take a long time (the professor recalled launching the installation of a guest OS before dinner, knowing that it would take the whole dinner to complete: not acceptable if speed is needed). With containers the guest OS is not present, so creating a new container simply means changing some parameters in the cgroups and in the namespaces to create the new controlled environment for a group of processes: it is immediately ready, since it just means launching processes as usual and putting some constraints on them.
\item \textbf{Isolation.} Achieved only to some extent, thanks to namespaces, but the strong isolation of VMs is lost, because the resources are shared by everything: the operating system is always one.
\end{itemize}

It is therefore wrong to say that each container has a different operating system; the correct statement is that \textbf{all containers share the same operating system}, which is the opposite of what happens with virtual machines. Tools that bundle the code of the processes with all the required libraries and dependencies turn them into executable units of software ready to be launched as needed.

\section{Containers and virtual machines}

Containers and virtual machines both provide isolated execution environments, but they differ in their abstraction boundary and resulting trade-offs.

\subsection{Conceptual architecture comparison}

A virtual machine typically consists of an application stack running on a guest operating system, which runs on virtual hardware provided by a hypervisor. Multiple virtual machines can share the same physical host, and each virtual machine includes its own kernel and system services.

A containerized architecture typically consists of multiple application stacks running as isolated process groups on a shared host operating system. A container runtime (sometimes called a container engine) configures namespaces and cgroups and manages container images. The kernel and most device drivers are shared across containers.

In the figure of the slides, on the left, the physical infrastructure hosts a hypervisor and, on top of it, virtual machines each with a guest OS, binaries and libraries needed to run the software. That is only one way to do traditional virtualization: since there is no host operating system, the hypervisor is of type 1; with a host operating system between hardware and hypervisor it would be type 2. In containerization there is instead the physical hardware, always a host operating system, a container engine and finally the containers. The \textbf{container engine} is the userland configuration tool set that makes the use and control of cgroups and namespaces more user-friendly, and each container bundles not only the application code but also binaries, libraries and all the dependencies required to run that code on that specific host operating system.

\subsection{Performance and density}

Containers are generally faster to start, stop, freeze, and dispose than virtual machines because container creation does not require booting a guest operating system. Containers are lighter in terms of CPU and memory usage because they avoid instruction emulation and avoid duplicating kernel memory. These properties enable higher density, meaning that more isolated workloads can be hosted on the same physical machine.

With mature kernel implementations, containerization can achieve performance close to native execution for many workloads, since system calls and scheduling operate directly on the host.

In more detail, containers are faster than VMs from any point of view: to \emph{boot}, because there is no operating system to activate; to \emph{freeze}, \emph{dispose} and \emph{orchestrate}, because they use fewer resources and are therefore easy to stop and to isolate from the others. They are lighter because they use less CPU, since they are only processes governed by some constraints, and less memory for the same reason, and they do not require the full virtualization overhead of typical hypervisors. This makes it easier to reach a performance close to the native one: the difference between normal processes and container processes is just some controls to perform, which absorb some CPU cycles, but there is none of the emulation of full virtualization, where, as recalled, the guest was unaware to be a guest and the hypervisor had to translate instructions on the fly.

\subsection{Isolation and flexibility}

Virtual machines typically provide stronger isolation because the hypervisor boundary separates guest kernels from the host. This can mitigate the impact of guest kernel exploits and reduces shared kernel attack surface. Virtual machines also enable running different operating systems on the same host.

Containers provide isolation primarily at the process level. Their security depends heavily on correct configuration, kernel hardening, and careful management of privileges. Containers cannot directly provide a different kernel per workload.

Virtual machines still have some positive aspects. First, they provide better isolation: suppose that an attacker gets control of the kernel of the system; at that point all the containers are immediately reachable by the attacker, whereas with VMs, if the kernel of the host OS were attacked the guest OS could still be protected, and if only one VM were attacked the others would surely be protected. Second, they provide better security because, with VMs, the number of attack points is more limited: in particular a type 1 hypervisor is particularly tiny, so it has few lines of code that can be attacked. Finally, with virtual machines there is no limit (compatibly with the available resources) to the operating systems that can run on the same physical machine: one VM with Windows, one with Linux, one with macOS, one with another Linux distribution. With containers on a Linux physical computer all containers share Linux, so the possibility of testing different applications on different operating systems within the same computer is lost.

\subsection{Containers or virtual machines?}

Which one is better depends on the application. If stronger isolation and security are wanted, performance is not a concern (waiting some minutes for the virtual environments to be created is acceptable) and perhaps different operating systems on the same machine are preferred, virtual machines are better. Conversely, if flexibility, dynamism and speed are the main requirements to provide services in the cloud, containerization is the approach to follow. Indeed, nowadays cloud providers mainly use containers orchestrated with software such as Docker and Kubernetes, discussed in the next lectures, which provide very good performance at the price of losing some security. For this reason a lot of recent research on cloud security focuses on containerization rather than on VM management, because that is where most issues are.

\section{Use cases for containers}

Besides virtual machines, which have their own purposes, containers are very useful. The main scenarios are:

\begin{itemize}
\item \textbf{Cloud computing}: containers are perfect to be deployed easily and rapidly whenever they are needed, and they are easy to migrate from a public cloud to a private one and vice versa, which fits the hybrid cloud architecture seen in the previous lectures.
\item \textbf{Application modernization}: bundling an application before migrating it from an on-premises infrastructure to the cloud.
\item \textbf{DevOps}: the programming paradigm according to which software should be built, shipped and run as fast as possible; containerization makes it easy to build such pre-built packages.
\item \textbf{Microservices}: a very important scenario, a programming paradigm that has become particularly widespread in the last ten years. Being more complex to discuss than the others, it is analyzed in the following section.
\end{itemize}

\section{Microservices and the role of containers}

Among the use cases of containers, microservices are the one most closely related to cloud computing: nowadays deploying services based on microservices as cloud services has become quite common, because the two philosophies, microservices and cloud computing, share a lot of features. Before looking at concrete container implementations (Docker, and containers managed by Kubernetes), it is therefore worth analyzing this use case in greater detail, to understand why containers in general, and LXC containers in particular, are well suited to it.

Modern applications are increasingly designed as collections of cooperating components rather than as monolithic systems.

\subsection{Monolithic applications}

A \emph{monolithic} application is designed, developed, and deployed as a single unit. All the routines and functions required to provide the sub-services of the main service of the application are implemented within the same application, that is, in the source code of the main application itself. A monolith often integrates multiple logical components, such as a web server, application logic, and a database, within one deployment artifact and one operational boundary. A common example is a web application stack composed of a Linux operating system, an HTTP server, a database server, and a scripting or application runtime.

\begin{notebox}
	\textbf{Example: an e-commerce platform.} Consider a platform like Amazon. It has to provide several sub-services: the \emph{catalog}, through which users search for products; the \emph{cart}, in which each consumer temporarily saves the items before buying them; \emph{account} creation and management; the management of \emph{orders}; and the \emph{processing of payments} with credit cards. With the monolithic paradigm all these features are implemented in one single application, which is then activated as a process either on an on-premise infrastructure or on a cloud infrastructure. This means that all the sub-functionalities are \emph{tightly coupled}: they are strictly connected to each other, because the life of one is also determined by the way the others are living.
\end{notebox}

Monolithic applications are not bad in general. If the service to create is small, for example just three main functionalities with a limited number of lines of code each, a monolithic application can easily be created, run, and also scaled, because the sub-services are tightly coupled but all of them are small. Conversely, for a very big web service such as an e-commerce portal, the monolithic paradigm is not the most suitable and convenient one. There are four main reasons.

\subsubsection*{Multiple programming languages}
\addcontentsline{toc}{subsubsection}{Multiple programming languages}

With the LAMP stack (Linux, Apache, MySQL, PHP) multiple programming languages are already introduced, together with the custom glue code that connects the components. Not all operating systems or platforms where the monolithic application is going to run support applications written in multiple languages.

\subsubsection*{Maintainability}
\addcontentsline{toc}{subsubsection}{Maintainability}

Suppose that a developer must update only one routine of the application, for example the one that processes payments, because a new kind of payment with a different type of card has to be supported. After the update is committed to the internal repository of the company, a monolithic application requires \emph{retesting everything}: since everything lives in a single source code, the modification touches the core of the application and nobody knows whether it has impacted the way the other subroutines work. Managing a monolith with thousands of lines of code therefore requires a lot of time for testing, since all the prepared tests must be repeated for any change in any sub-service, and most likely also a lot of time for fixes: it is quite likely that the change interferes with the other subroutines, which then also have to be modified to be compatible with the update.

\subsubsection*{Scalability}
\addcontentsline{toc}{subsubsection}{Scalability}

Suppose that the e-commerce platform is deployed on a cloud infrastructure and that the subroutine dedicated to the catalog needs more power, because many customers access it at the same time (for example during a Black Friday event). A first solution is to deploy multiple instances of the process of the application. But the application is monolithic: scaling it does not duplicate only the catalog sub-service, \emph{everything} is multiplied. Even if it would have been enough to duplicate the catalog, there are also multiple copies of the payment, cart and accounting sub-services, and so on. All this is extra overhead and is totally useless, because there was no overload of traffic directed to those sub-services.

\subsubsection*{Fault propagation}
\addcontentsline{toc}{subsubsection}{Fault propagation}

When multiple sub-services are integrated in a tight way in the source code of a single application, a fault in any one of them, while the process is running, most likely makes the others unavailable too, or at least impacts their performance.

\begin{notebox}
	\textbf{In short.} Monolithic design leads to: a cumbersome development and testing process (changes to any component may require rebuilding and revalidating the entire application); difficulty updating or scaling individual components, since they are tightly coupled; limited scalability flexibility, because scaling replicates the entire monolith even when demand concentrates on a specific function; and propagation of faults across components.
\end{notebox}

\subsection{Microservices and the single-responsibility principle}

For these reasons, a new development paradigm was proposed already at the end of the last century (the slides report that microservices were proposed in 1998 at Amazon): the paradigm based on \emph{microservices}. The idea is the opposite of the previous one. An application characterized by multiple sub-functions does not implement them as routines of the same program, but as \emph{separate programs}, separate services named microservices, because each one is most likely smaller than the monolithic application that would have resulted if all of them had been implemented in a single source code.

A \emph{microservices} architecture arranges an application as a collection of loosely coupled services. Each service supports a single business task and is designed to be independently deployable.

\subsubsection*{Loosely coupled services}
\addcontentsline{toc}{subsubsection}{Loosely coupled services}

\emph{Loosely coupled} means that each microservice lives by itself, but has at least some loose relationship with the others, because they must interact: they are part of the same big purpose of the original monolithic application. In the e-commerce platform, the payment microservice must contact the accounting one to get information about the person who is paying; the microservice that saves items in a wish list must interact with the catalog microservice to understand which items are being saved.

These relationships are no longer based on the invocation of functions, as in monolithic applications, but on \textbf{network communications}. The process of a microservice communicates with the process of another microservice through a network, which may also be the internal network of the server where they run, using virtualized networks in which no packets go outside of the server. Service boundaries therefore shift inter-component interactions from in-process function calls to network communication. The communications may follow different paradigms:

\begin{itemize}
\item \textbf{REST APIs}: a way to define programming interfaces according to some philosophies, based on the way resources are accessed (they are studied in more detail in the distributed systems programming course). Microservices commonly interact using request-response communication, frequently implemented with REST-style HTTP APIs;
\item \textbf{gRPC}: an advanced version of remote procedure calls;
\item in general, any paradigm based on the invocation of external services, with communications happening over the network.
\end{itemize}

This adds complexity, but it brings a benefit: microservices are small. Whenever one of them must be modified, only the source code of that microservice is changed and only that microservice is tested; the others are expected not to be impacted and, at most, one verifies that the REST API exposed by the modified microservice still works as expected. In the same way, scaling a microservice means duplicating it as many times as needed, without duplicating the other microservices, for which one instance each may be more than enough.

\subsubsection*{The single-responsibility principle}
\addcontentsline{toc}{subsubsection}{The single-responsibility principle}

Microservices cannot be made smaller and smaller indefinitely: a criterion is needed to identify their proper size. This criterion is the \emph{single-responsibility principle} (SRP). A software module should be responsible to one, and only one, actor, where an actor is a group of stakeholders or users that requires a change in that module. Applied to microservices, the principle motivates creating services whose evolution is driven by a well-defined set of requirements and stakeholders, reducing cross-cutting changes across unrelated functions. In other words, each microservice should contain all the sub-functionalities required to perform one specific goal, one specific responsibility, completely implemented in it.

\begin{notebox}
	\textbf{Example.} The payment processing microservice should have everything needed for the successful operation of a payment, without requiring further sub-services below it (one for managing one specific type of card, another one for the others, and so on). The goal is one, managing payments, so the microservice should also be one. Otherwise two too fine-grained microservices are created, and making them interact becomes difficult, because communications would be excessive.
\end{notebox}

\subsection{Architectural consequences}

In a monolith, the user interface, business logic, and data access layers are typically compiled and deployed together. In a microservices architecture, the user-facing component interacts with multiple back-end services, and each service can have its own data store. The resulting system resembles a network of services where each service exposes an API and can be scaled, updated, and deployed independently.

\end{center}

The figure shows the migration from a monolithic to a microservice architecture. In the monolithic architecture (right) everything is jointly coupled: a user interface, a business logic with many internal functions, and a data access layer with the database. In the microservice architecture (left) everything is separated. The user interface is the first access point of the users to the ecosystem of microservices, and as its backend there is typically an \textbf{API gateway}: a microservice responsible for receiving all the external requests and for understanding to which microservice each of them must be routed.

Each microservice, after receiving a request, needs some information to provide an answer. Sometimes the information is local; other times it must contact another microservice to get it. In the previous example, the payment processing microservice contacts the accounts microservice to retrieve information about the person making the payment. These communications are the lines connecting the microservices in the figure: they may be calls to REST APIs, gRPC, or any other inter-process communication paradigm, but they always occur through a network. Each microservice listens on a certain port and sends messages through the corresponding socket.

\subsubsection*{Database access}
\addcontentsline{toc}{subsubsection}{Database access}

There are several ways to manage the access to the databases:

\begin{itemize}
\item one (or two) microservice(s) are dedicated to database access, and all the other microservices must contact them whenever they need to write or retrieve data;
\item (very common) most microservices access the database by themselves. The databases may be separate, or they may be only \emph{logical} separations of the same database, for example using control groups or namespaces to control the way the different processes use these resources or have visibility on them. Each microservice is one process, so the processes can be grouped with the features seen in the previous lecture.
\end{itemize}

\subsection{An example: Uber}

The microservice paradigm is more and more used by big companies to create their applications. A well-known example is the Uber application, an app for booking rides in taxis, widely used all over Europe (perhaps less in Italy). Its sub-services include: passenger management, with all the information about passengers; payments, which allow consumers to pay the drivers; a part for the drivers, who declare their availability to be contacted by customers; notifications, such as pop-ups on the smartphones of the users; billing; and trip management, which allows any user to understand how much time is needed to go from a location to another.

	\safeimg[width=5in]{media/image175.png}
\end{center}

In the original \emph{monolithic} version (left in the figure) all these sub-services were implemented in the source code of one single application. Everyone and everything had to contact this single application: drivers, passengers, the adapters related to the sub-services (for example the Stripe adapter for payments), and also the web user interface.

In the current \emph{microservice-based} version (right in the figure) each sub-service is a separate microservice, that is, a separate process. The microservices interact with each other through inter-process communications such as REST APIs and gRPC, while the \textbf{API gateway} is the access point of external users (drivers or consumers) to the ecosystem: it redirects their API calls to the specific sub-services. Moreover, not every microservice communicates with all the others: the APIs exposed by each one are designed only for the microservices that need to interact with it. For example, trip management only provides REST APIs to the API gateway, for external users, who are interested in organizing a trip; the notification and payment sub-services are not interested in organizing trips, so the trip management microservice exposes no REST APIs for them.

\begin{itemize}
\item \textbf{Functionality reuse.} A very big application is only useful for the purposes for which it was created. Each microservice, instead, can be used in the ecosystem of a different application: the payment processing microservice may serve the e-commerce platform and any other application that must manage payments. It is created once and reused anywhere, as long as its APIs are self-explanatory enough.
\item \textbf{Communication.} In the monolithic version, sub-functions call each other with function calls, as in most software programming. Microservices typically use APIs such as REST APIs based on the HTTP protocol.
\item \textbf{Technological flexibility.} A monolith is typically written in a single language, because otherwise it is difficult to let a function in one language invoke a function in another within the same source code. Microservices have no such limitation: each may be written in a different language, since what matters is that the processes can communicate over the network.
\item \textbf{Data management.} Monoliths typically have centralized access to data; microservices may use a centralized one but, in many scenarios, a decentralized one in which each microservice contacts its own copy of the database.
\item \textbf{Resiliency.} If the process of a monolith has a problem, the whole process is down and no longer accessible. If one microservice fails, all the others can continue to work, although in a limited way: if the payment microservice of the e-commerce platform fails, customers cannot pay, but they can still consult the catalog, save items in the wish list, modify their account information, and so on.
\item \textbf{Scalability.} Each microservice can be scaled independently from the others, whereas in a monolith everything is scaled every time a copy of the process is created.
\end{itemize}

\subsection{Why containers fit microservices}

Microservices may live on the same host and in the same operating system, but they should be loosely coupled, that is, as independent from each other as possible. \emph{How} can they be implemented?

\begin{itemize}
\item \textbf{Virtual machines.} Using VMs is still possible, but it is not the recommended solution. Microservices are designed to be small and lightweight, each corresponding to a very small number of lines of code; a virtual machine virtualizes the hardware and then the operating system, so it introduces more overhead than the resources required by the single microservice (the slide describes a VM as a server hosting multiple components: heavy and inefficient).
\item \textbf{Containers.} The inefficiency is avoided by implementing microservices with containers: the processes representing the microservices are simply managed with cgroups and namespaces, without any additional overhead.
\end{itemize}

Containers provide a practical unit for packaging and executing microservices:

\begin{itemize}
\item \textbf{Self-contained deployment}: a container image bundles the service and its dependencies.
\item \textbf{Low overhead}: many service instances can run on one host.
\item \textbf{Fast start}: scaling a service can be accomplished by starting additional container instances; it is enough to replicate the processes and put them in the same groups or namespaces as the ones related to the same feature.
\item \textbf{Composability and replaceability}: service instances can be started, stopped and replaced easily, because containers are just groups of processes and there is no need to install an operating system every time one of them is activated. This facilitates rolling updates and rapid iteration.
\end{itemize}

\section{Operational challenges of microservices}

While microservices improve modularity and independent deployment, they introduce operational complexity: new challenges arise because function calls can no longer be used for communication between components.

\subsection{Communication and addressing}

The first challenge concerns \emph{new programming paradigms}: microservices communicate over the network rather than using local interprocess communication mechanisms, so new paradigms such as REST APIs or gRPC are needed. Services cannot assume that a dependency is reachable via localhost or shared memory. Instead, each service must locate other services using network addresses or names (``which is the IP address of the database I need to connect to?''). If service instances scale dynamically, hard-coding addresses becomes infeasible.

\subsection{Need for orchestration}

The second challenge, not mentioned so far, is \emph{orchestration}. It is necessary to simplify the way microservices can reach each other and to simplify their management for human users. A human user cannot be expected to understand when a microservice must be scaled: all the decisions about providing communications for the microservices and about scaling them must be managed by automatic tools. These tools are the \textbf{orchestrators}, developed over the years to manage microservices and, in general, containers themselves. Scaling microservices independently requires mechanisms to:

\begin{itemize}
\item schedule service instances onto available machines,
\item manage service discovery so that services can find each other,
\item provide load balancing across replicas,
\item detect failures and replace failed instances,
\item coordinate configuration as services move and scale.
\end{itemize}

These requirements motivate dedicated container orchestration systems.

\section{Container deployment and orchestration}

The deployment and orchestration of containers is not a trivial problem at all: it can be approached in different ways, with increasing levels of automation.

\subsection{Manual deployment}

A first way to deploy, scale and maintain containers is to perform manual operations: a cloud administrator uses a protocol such as SSH to interact with the machines and the containers and runs some instructions to manage them. In computer networking and cloud computing manual configuration is always possible; one could do it, for example, for the ARP tables of the devices, even if it is not recommended, because IP addresses change continuously and a static ARP table is soon outdated. The same holds here.

The advantage is simplicity and availability: the administrator does not need to choose the best tool, install it and learn how to interact with it, but reuses protocols like SSH, which are intuitive and which everybody has used in their work as cloud administrators. No additional tooling beyond remote access and the container runtime is required.

The disadvantages are many. Operations are not automated, so a human must constantly understand how much traffic reaches each container and whether it must be scaled. Whenever a container has a problem, the user must understand why it happened and heal it, without \emph{self-healing} features, that is, automatic mechanisms that find the root cause of the problem if needed, kill the container and start another one of the same type. The approach is also difficult to reproduce reliably. Managing two or three containers manually may still be feasible (and not everyone needs to operate at scale, so this method may not be that bad), but in the context of a cloud provider it is completely impractical.

\subsection{Deployment via scripting and configuration management}

The first level of automation is a \emph{partial} automation via scripting. No orchestrator dedicated to the lifecycle management of all the containers is used; languages and tools such as \textbf{Puppet, Chef, Ansible and Salt} (or just custom-made scripts) allow writing \emph{reproducible} scripts, that is, sequences of code lines that repeat the same operations every time they are executed, and automate specific subroutines of container management. Such approaches improve reproducibility, integrate with existing operational environments, and give easily understood results.

However, they retain several limitations:

\begin{itemize}
\item \textbf{manual scheduling} of the containers on the machines;
\item \textbf{not scalable}, because someone must launch the script every time and understand that there is the need to activate it;
\item \textbf{no self-healing}: when an issue occurs, the human must understand it and execute the remediation actions, so at most the remediation is automated, not the understanding of the issue;
\item \textbf{generally not portable}, because scripts contain code related to a specific environment.
\end{itemize}

\begin{notebox}
	\textbf{Scripts versus Dockerfile.} The scripts discussed here are scripts for \emph{managing} containers. A Dockerfile is a different thing: it is not a script for orchestrating Docker, but a script that provides the information needed to create \emph{one} container. Docker combines both: there is a script (the Dockerfile), which after some steps becomes a container, and then the containers are managed by a Docker orchestrator. The Dockerfile and the orchestrator are discussed separately in the following sections.
\end{notebox}

\subsection{Dedicated orchestrators}

The best approach is a \emph{dedicated} orchestrator, that is, software specifically created for container management (not a generic software customized for it). A dedicated orchestrator automatically matches containers to machines, avoiding human intervention, and manages lifecycle tasks. This can include scheduling based on resource needs, enforcing affinity constraints, managing replication, handling machine failures, and providing service discovery. Examples:

\begin{itemize}
\item \textbf{Docker Swarm}, the orchestrator of the Docker ecosystem, in charge of managing the lifecycle of Docker containers;
\item \textbf{Kubernetes}, which manages various types of containers with a very peculiar architecture (discussed in the next lecture). Today it is the \emph{de facto} standard for container orchestration, also because it can manage Docker containers themselves;
\item \textbf{Mesos};
\item home-grown systems: a very big company may create its own orchestrator, although this is not the case typically followed in enterprises.
\end{itemize}

The advantages are that everything can be automated, reproducible, scalable, portable and self-healing. The disadvantages are mainly the overhead of knowledge needed to understand how to use these tools, each of which must be used by human users and whose approach is not straightforward (in Kubernetes, for example, the way containers are deployed and interact is more complex than just providing a REST API and letting others contact them), and the fact that their outputs are more complex and not immediately intelligible. These cons are mostly limited to the training of the users: once a person has learned how to use an orchestrator, the advantages are much greater than those of manual or script-based orchestration.

\subsection{Orchestration goals}

Orchestration systems aim to provide a combination of essential (must-have) and optional (nice-to-have) capabilities. The list below is not exhaustive.

\subsubsection*{Core goals}
\addcontentsline{toc}{subsubsection}{Core goals}

\begin{itemize}
\item \textbf{Container lifecycle management}: start, stop, restart, and remove containers reliably.
\item \textbf{Scheduling}: deployment of the containers, that is, deciding which piece of hardware, which physical server, is the best one for each container, based on resource requirements (CPU, memory), affinity constraints, and labels. The research literature contains many scheduling algorithms that optimize different parameters (CPU usage, memory usage, communication latency, affinity requirements based on the functionalities of the containers, and so on). An orchestrator may embed several scheduling algorithms and a human decides which one is most suitable for the scenario in which the orchestrator is used.
\item \textbf{Replication} (scalability): an automated mechanism to replicate a container and run a specified number of replicas for fault tolerance and throughput.
\item \textbf{Failure handling} (self-healing): an automated mechanism to handle any failure of the containers or of the machines hosting them, rescheduling workloads.
\item \textbf{Discovery}: automatic ways for each container to find the other containers in the same network.
\item \textbf{Inspection}: constantly observing how the system works and reporting any problem to human users. In cloud computing it is also useful for \emph{billing}, since it gives an idea of how much traffic goes to which container.
\item \textbf{Virtual networking}: managing the communication among containers (virtual networks and tenant isolation). The last theoretical lectures of the course (about four hours) are dedicated to virtual networking, with the paradigms \textbf{SDN} (Software Defined Networking) and \textbf{NFV} (Network Functions Virtualization), which provide ways for the automatic management of virtualized computer networks.
\end{itemize}

\subsubsection*{Additional goals}
\addcontentsline{toc}{subsubsection}{Additional goals}

These are non-mandatory features, not implemented by all orchestrators (many of them, however, are implemented in Kubernetes, which is why it has become so common):

\begin{itemize}
\item \textbf{Load balancing}: distribute traffic among replicas.
\item \textbf{Automated updates}: perform rolling updates and rollbacks.
\item \textbf{Autoscaling}: scale clusters and applications based on utilization and demand (cluster auto-scaling for better utilization, app auto-scaling to handle spikes and troughs).
\item \textbf{Storage provisioning}: provide persistent storage abstractions.
\item \textbf{Automatic restart}: restart an application when it crashed.
\item \textbf{Late-binding configuration}: inject configuration at deployment time rather than baking it into images.
\end{itemize}

\section{Docker as a container platform}

Docker is a widely used platform for building and running Linux containers. It is more than a container implementation: it is an \emph{ecosystem}, a full suite of elements that specifically improve the user-friendliness of container management, and it is the first ecosystem that made the usage of containers popular all over the world.

Today ``Docker'' and ``containers'' are sometimes used as synonyms, but they are not: Docker still uses Linux containers and enriches them with other features. The confusion arises because the userland of tools provided by Docker was much better than the one available with LXC containers by default, but containers existed years, even decades, before these tools were created. Container-related technologies existed before the public release of Docker in 2013; Docker \emph{democratized} containerization by bringing it to the masses through a developer-friendly and cloud-friendly implementation. Docker is built on the virtualization technology of LXC containers and provides more user-friendly features for developers to build, deploy and manage containers, accessible through simple commands and automated through an application programming interface (API).

\begin{notebox}
	\textbf{Security.} The Docker slides also list \emph{secure} among the advantages, but security, as usual, is not so strong when dealing with containers, and Docker does not provide much better security than normal LXC containers. Security is discussed in the second part of the course (second semester).
\end{notebox}

\subsection{Motivations and differentiating features}

Compared with the traditional LXC containers discussed so far, Docker offers additional features.

\subsubsection*{Portability}
\addcontentsline{toc}{subsubsection}{Portability}

LXC containers are typically machine dependent: a container created for one operating system may work there but is not portable to others (perhaps to some, but not many). Docker makes it easier to move a container from one machine to another, even if they have different characteristics: container images run without machine-specific configuration across desktops, data centers, and cloud environments. In part, this is possible because some applications of the Docker ecosystem, such as \emph{Docker Desktop}, hide the presence of a virtual machine, with some peculiar characteristics, that allows running a Linux container; this is hidden from the user and done in the lightest way possible, to avoid consuming too many resources.

\subsubsection*{Granular updates}
\addcontentsline{toc}{subsubsection}{Granular updates}

Each microservice can be maintained independently because microservices are separate containers. With Docker, however, one can also put several processes in a single container and modify one of them while the others continue to work as expected: granular updates are possible \emph{inside} the container itself. With LXC, instead, several processes can be combined in a container, but they can only be controlled as a group from the outside.

\subsubsection*{Automated orchestration}
\addcontentsline{toc}{subsubsection}{Automated orchestration}

Docker allows automated container orchestration thanks to the \textbf{Docker Swarm} orchestrator. According to the slides, Swarm is integrated with Docker and mainly developed by the same company, focuses on ease of use and easy setup, scales to thousands of machines, but its use is shrinking nowadays. Using Swarm is not necessary: a single user who wants to activate one container can do it manually with the \texttt{run} command, starting the container from an image (the \texttt{run} can be executed manually or by an orchestrator). A cloud provider, on the other hand, needs an orchestrator such as Swarm, because activating all the containers manually is unfeasible.

\subsubsection*{Automated container creation}
\addcontentsline{toc}{subsubsection}{Automated container creation}

Docker can automatically build a container based on the application source code, through the Dockerfile described below.

\subsubsection*{Container versioning}
\addcontentsline{toc}{subsubsection}{Container versioning}

Docker can track the versions of the changes applied by a developer to an application. This information is stored in an object called \emph{image}: a read-only piece of information that contains all the layers of the previous changes and allows restoring, or rolling back, to a previous version whenever needed. Each layer tracks how binaries, code, etc.\ were modified with respect to the previous versions, so one can simply go back to a previous one because everything about the changes is known, in a way similar to commits on a GitHub repository. Docker can also trace who built a version and how, and upload only the deltas between an existing version and a new one.

\subsubsection*{Shared container libraries}
\addcontentsline{toc}{subsubsection}{Shared container libraries}

The main reason why Docker became successful is that it provides shared container libraries, such as the Docker registry. Each developer can make available to the others, through images, the containers they have created, and anybody who wants to create a container does not need to start from scratch: they can take an image pre-created by another developer and slightly modify it. For example, to modify something in an Apache container, one takes an image provided by someone who has already added all the dependencies needed to run Apache and adds just some lines of code to alter its behavior slightly. This starts from a very pre-built knowledge for the creation and management of containers, something that could never be done with standard LXC containers.

\begin{notebox}
	\textbf{An analogy.} A registry works like a library of functions used to develop programs: it is a library of ``partial containers'', the container images, that can be reused to build one's own.
\end{notebox}

\subsection{Key concepts and components}

Docker-based systems are commonly described using a set of core terms: Dockerfile, Docker images, Docker containers, Docker daemon and Docker registry. They are the basic entities of the Docker ecosystem, managed by the Docker daemon with the help and support of the Docker registry. The chain that leads from the description of a container to a running container has three steps, which are explained in the following paragraphs.

\begin{center}
	\safeimg[width=4.5in]{media/image177.png}
\end{center}

\subsubsection*{Dockerfile}
\addcontentsline{toc}{subsubsection}{Dockerfile}

A Docker image is typically built from a text file called a \emph{Dockerfile}. The Dockerfile is the basic element from which one starts to define how a container should behave: it is a very simple and user-friendly file in which a sequence of instructions specifies how the container image has to be created when the file is built. If a container must run a certain software, which requires specific dependencies, binaries and libraries, the Dockerfile is the place in which all of this must be written: that the software is going to be installed and that these binary dependencies and libraries are needed to make it work. Afterwards the Docker daemon, a process of the Docker engine, takes the Dockerfile and creates a Docker image starting from it.

A Dockerfile specifies instructions that the Docker engine executes to assemble an image. The instruction set is extensive but standardized, so builds are reproducible across environments. Writing a Dockerfile does not require any specific knowledge beyond the common commands of the Linux command line interface, because the Dockerfile is a series of command line interface instructions, which the Docker engine (specifically the Docker daemon process) parses in order to assemble the final image.

\subsubsection*{Images and layers}
\addcontentsline{toc}{subsubsection}{Images and layers}

A Docker \emph{image} is a read-only template that contains application code and all required dependencies. It is created by invoking the \texttt{build} command on the Docker daemon, which automatically builds it starting from the Dockerfile. The image is \emph{not} the active container: when the Dockerfile is written one is not yet ready to instantiate the container, the image must be created first. It is a pre-assembled, passive entity, as if one had a bundle of all the software ready to be executed, but not executed yet.

Building the image from one's own Dockerfile is possible, but today it is not the standard procedure. A very large number of Docker images are available in open-source repositories, the \emph{Docker registries}, to which the developers who created them have pushed them. The standard way to create an image is to \emph{pull} an already existing image from a registry and add what is needed, such as a new dependency or new configuration parameters of the main software. In this way one does not reinvent the wheel every time, rewriting the full Dockerfile, but takes an existing image and adds only the bit of information required to provide more features. Moreover, many images shared in the registries have a lot in common in their stack: whenever there is an issue in the common part, it is enough to apply some changes to the so-called \emph{base image} from which all of them started, and all of them get the variation immediately, because the modification is reflected on all the images that share the same base.

Images are composed of \emph{layers}, where each layer represents a build step. Any time a modification is applied to an image (the one built from a Dockerfile, or one pulled from a registry and extended) a new top layer is created, and previous layers remain available for reuse and rollback.

\begin{notebox}
	\textbf{Layers and git.} A layer can be thought of as a commit in a git repository: a commit contains the information about the differences of the new files with respect to the previous ones, and in the same way every layer specifies how the things that were included earlier have been modified. As with a git repository, one can \emph{roll back} to previous commits if not satisfied by the newer ones: with Docker, at any time one can return to the configuration of the image given not by the top layer, but by an intermediate or by the bottom one.

	\medskip
	This also gives higher flexibility in \emph{reusing} an image. Another developer is not required to start from the top layer: one may start from the bottom (the vanilla image), another from an intermediate layer, because perhaps they do not want the latest features introduced in the last layer, which may be too invasive in terms of memory usage. Every intermediate layer is therefore a possible starting point, a possible new base image to create new ones.
\end{notebox}

\subsubsection*{Containers}
\addcontentsline{toc}{subsubsection}{Containers}

A Docker \emph{container} is a running instance of an image. To summarize: Docker images are just the software of the main program of the container (binaries, dependencies and libraries packaged together), which is similar to the definition of container given in the introduction to containerization, but they are not containers, because they are passive, read-only entities that are not running. When the \texttt{run} command is invoked on the Docker daemon for one image, the next step of the chain is performed: from the read-only image a container is created, which is a live, running instantiation of the software with the dependencies specified in that image.

The image can therefore be seen as a \emph{blueprint} to instantiate containers, and as many containers as needed can be instantiated from a single image. Every time a new one is needed there is no need to repeat the whole process of writing the Dockerfile and building it: it is enough to take the image and ask the Docker daemon to run a corresponding container. This can be done also days, weeks or years after the image was built. Containers are ephemeral in the sense that they are intended to be disposable and recreatable. Users can interact with containers, and administrators can adjust runtime settings using Docker commands.

From the technological point of view, Docker containers are based on the same concepts seen for LXC containers: at low level they use namespaces and control groups to provide resource visibility control and resource usage limitation for the groups of processes combined inside one container. The low-level features are the same, but with respect to LXC containers there is no need for a human user who specifies the sequence of commands for the containers themselves: the intermediate passage through the Docker image provides an easier instantiation.

\subsubsection*{Docker daemon and host}
\addcontentsline{toc}{subsubsection}{Docker daemon and host}

The Docker \emph{daemon} is a service that creates and manages images and containers. It is an essential process of the Docker engine, in charge of answering all the commands coming from the client (all the operations of building and running are managed by it). The machine on which the daemon runs is the Docker \emph{host}. Clients interact with the daemon through a local or remote API.

\begin{notebox}
	\textbf{Remember the pair daemon/host.} These two names are also used in other platforms, including Kubernetes itself, as we will see below.
\end{notebox}

\subsubsection*{Registries}
\addcontentsline{toc}{subsubsection}{Registries}

A Docker \emph{registry} is a scalable, open-source storage and distribution system for images that any developer can access, to \emph{push} images after building them from their own Dockerfiles or to \emph{pull} images pushed by other developers. Images are organized into repositories and identified using tags. The existence of the registries created a community of developers who continuously help each other by providing images: nowadays nobody starts a Dockerfile from scratch. In the worst case one starts from the image of an already existing operating system such as Ubuntu; in most cases one starts from quite pre-configured images and just customizes them with new Dockerfiles that start from them.

Registries also allow tracking the changes of the different images by looking directly at their layers, and this is based on \emph{git} as the tracking tool. They enable version tracking and sharing of images, including incremental uploads of changes.

\subsection{Workflow: Dockerfile to image to container}

A typical workflow is:

\begin{enumerate}
\item define a Dockerfile that specifies how to build the software environment,
\item build an image from that Dockerfile,
\item run one or more containers from the image.
\end{enumerate}

\subsubsection*{A Dockerfile example: MongoDB on Ubuntu}
\addcontentsline{toc}{subsubsection}{A Dockerfile example: MongoDB on Ubuntu}

The slides show a Dockerfile that contains the most common instructions that are written before building. Its goal is to create a container running one instance of the MongoDB database, starting from an Ubuntu image.

\begin{codeblock}
# Dockerfile to build MongoDB container images, based on Ubuntu

# Set the base image to Ubuntu, with a specific tag (1910)
FROM Ubuntu:1910

# File Author / Maintainer
MAINTAINER Example McAuthor

# Update the repository sources list.
RUN apt-get update

################## BEGIN INSTALLATION ######################
# Add the package verification key
RUN apt-key adv --keyserver hkp://keyserver.ubuntu.com:80 --recv 7F0CEB10

# Add MongoDB to the Ubuntu default repository sources list
RUN echo 'deb http://downloads-distro.mongodb.org/repo/ubuntu-upstart dist 10gen' \
    | tee /etc/apt/sources.list.d/mongodb.list

# Update the repository sources list once more
RUN apt-get update

# Install MongoDB package (.deb)
RUN apt-get install -y mongodb-10gen

# Create the default data directory
RUN mkdir -p /data/db
##################### INSTALLATION END #####################

# Expose the default port
EXPOSE 27017

# Default port to execute the entrypoint (MongoDB)
CMD ["--port 27017"]

# Set default container command
ENTRYPOINT usr/bin/mongod
\end{codeblock}

\begin{itemize}
\item \textbf{FROM}: almost all Dockerfiles start with this command, which specifies the \emph{base image} from which the new image is created. Here an Ubuntu image with the tag 1910 is selected, which already has some dependencies for software to run on Ubuntu. This avoids replicating all the commands already specified in the Dockerfile from which that image was created. This base image is a straightforward one, but one may select a base image that already contains the installation of a web server, a database, etc., that is, a sort of pre-prepared platform.
\item \textbf{Metadata}: for example the \texttt{MAINTAINER}, which can be considered the author of the Dockerfile.
\item \textbf{Basic commands}, such as the update of the APT repository, as is usually done when installing libraries or tools from the command line of Debian-based operating systems.
\item \textbf{RUN}: the main part of the Dockerfile is a sequence of command line instructions prefaced by the \texttt{RUN} keyword. Each is a command that the Docker daemon executes, in order, when it must \emph{build} the image, that is, when it prepares the passive, prepackaged platform that will later be instantiated as a container. Here: first the package verification key is added, then MongoDB is added to the Ubuntu default repository source list, the APT repository is updated again, the MongoDB package is installed and the default directory for making it work is created. These instructions are \emph{not} executed when they are written, but later, when the image is built.
\item \textbf{Configuration of the future container}: besides the installation instructions, the first configuration instructions for the active container can be written. Here the port on which the MongoDB database service will listen is specified: 27017.
\end{itemize}

After the Dockerfile has been prepared, the image is built with the \texttt{docker build} command:

\begin{codeblock}
docker build --pull -t mymongo .
\end{codeblock}

\texttt{-{}-pull} requests to execute the build starting from the latest version of the image that is available, for example from the Docker registries; \texttt{-t} specifies the name of the image to create (here an image named \texttt{mymongo}); the final dot is the current folder, in which the Dockerfile is searched, but any path where the Dockerfile is located can be specified.

\begin{notebox}
	\textbf{Does the daemon check the Dockerfile?} No. The Docker daemon does not perform any check: it just takes what is written in the Dockerfile or in the corresponding image and tries the instantiation. At most the \texttt{run} fails, for example because the port is not available. Additional checks can be performed by auxiliary tools and also by the \textbf{Docker Swarm} orchestrator, which checks the life cycle and may verify, for example, the availability of the port on which a service must listen, and in some cases may even apply variations if allowed by the administrator of the orchestrator. Extra checks can also be added by the user, but then they are native in the image itself, completely customized for the scenario and written by a human, not managed automatically by an orchestrator. This is feasible, because anything that can be written in a batch script with command line commands can be rewritten in the Dockerfile, but it means writing more and having more difficulty in keeping everything under control.
\end{notebox}

\begin{notebox}
	\textbf{Base image versus operating system.} A base image such as Ubuntu is \emph{not} the full operating system: it only contains the minimum amount of libraries (drivers, libraries) that enable the Docker container to run on an Ubuntu-based operating system, that is, the compatibility requirements. The container should therefore preferably run on an Ubuntu host, because it shares the kernel of the Ubuntu operating system. If this is not possible, the \emph{Docker Desktop} application hides the presence of a virtual machine containing the operating system needed: a user on Windows can install Docker Desktop and launch the container built from the Dockerfile, which works because Docker Desktop hides a virtual machine that virtualizes a full computer with Ubuntu. The user friendliness is higher, but one goes back to full virtualization in these conditions.
\end{notebox}

The following example illustrates a minimal Dockerfile for a Python web service. It demonstrates the principle of declarative build steps, dependency installation, and container startup command.

\begin{codeblock}
FROM python:3.12-slim
WORKDIR /app
COPY pyproject.toml /app/
RUN pip install --no-cache-dir .

COPY . /app/
EXPOSE 8080
CMD ["python", "-m", "myservice"]
\end{codeblock}

The port value 8080 is written in a monospaced typeface because it is a computer-related value and frequently corresponds to a network service port.

\subsection{Docker architecture}

A Docker deployment is commonly organized into a client, a daemon running on the host, and one or more registries.

\begin{center}
	\safeimg[width=4.5in]{media/image178.png}
\end{center}

\begin{itemize}
\item The \textbf{client} issues commands such as build, pull, and run. The access point to the Docker host, where the engine runs, is the Docker daemon, which a user can interact with through a command line interface, remote APIs or, today, tools based on a graphical user interface. Commands may be executed locally on the host or transmitted to a remote daemon.
\item The \textbf{daemon} receives commands, builds images, pulls images from registries, and runs containers. When the client requests the build of a Dockerfile, the daemon accesses the file system of the Docker host to read it and create the corresponding image, which most likely is then put in the Docker registry. When the client asks to \emph{pull} an existing image, the Docker host, through the daemon, interacts directly with the registry to extract it. Whenever the client wants to \emph{run} an image, taken from the registry or from a local file system, the daemon is again the service in charge of making it active.
\item The \textbf{registry} stores images. When an image is pulled, layers are downloaded and cached.
\end{itemize}

In this arrangement, the daemon acts as the control center: it maintains local image storage, starts and monitors containers, and mediates network and storage integration. It is the basic fundamental block of everything, in charge of \emph{almost} everything: building images, interacting with the registries and instantiating containers.

\begin{notebox}
	\textbf{The Docker daemon is not an orchestrator.} It does not provide any of the features that characterize a container orchestrator: it does not manage the full life cycle of the containers, it does not provide self-healing when a container crashes, it does not check the memory and CPU usage of each container to verify that they reflect some required quotas. The list of must-have and nice-to-have features of an orchestrator seen in the previous lecture is almost entirely missing, simply because the daemon is not an orchestrator.

	\medskip
	In the Docker ecosystem the orchestrator is another piece of software, \textbf{Docker Swarm}, created by the developers of the ecosystem to interact natively with the Docker daemon and all the other elements of the system. With it there is no need to write scripts to run containers any more: one specifies the number of containers wanted and some requirements in terms of memory and CPU usage, and everything is set up and maintained automatically over time.
\end{notebox}

\begin{notebox}
	\textbf{A paradox.} Docker containers are today among the most commonly used containers, but Docker Swarm, which should be the native orchestrator, is \emph{not} the most commonly used one. Over the last 10--15 years another orchestrator got much more popular, thanks to a lot of nice features that were introduced there and that Swarm lacks. It is also supported by a very active community of developers on open-source repositories, and it has been adopted by the big players of cloud computing, starting from Google, Amazon and Microsoft. It is almost definable as the \emph{de facto} orchestrator choice for containers, so even when Docker containers are used they are orchestrated with this other orchestrator: \textbf{Kubernetes}. In the laboratory activities the students will not start by writing a Dockerfile: they will first pull a Docker image from the registry, then modify it and instantiate it to see how everything works in practice.
\end{notebox}

\section{Why orchestration becomes necessary}

As the number of containers increases, managing them becomes complex even on a single machine. The main sources of complexity are:

\begin{itemize}
\item \textbf{Deployment}: ensuring the desired number of instances is running and updated.
\item \textbf{Networking}: connecting containers and exposing services reliably.
\item \textbf{Management}: observing state, enforcing policies, and recovering from failures.
\end{itemize}

These concerns motivate orchestration systems that provide a declarative control plane.

\section{Kubernetes as a container orchestration platform}

Kubernetes is a container orchestration platform for scheduling and automating the deployment, management, and scaling of containerized applications. It manages the full life cycle of containers, from their deployment and management to self-healing, or the stopping of a container when it is no longer needed, providing the flexibility and scalability required by any cloud provider: for this reason a large majority of cloud platforms are today based on Kubernetes. Kubernetes is designed as a composable system that can manage large clusters and has been widely adopted.

\begin{notebox}
	\textbf{Why ``k8s''?} Kubernetes is often abbreviated as \emph{k8s}. The name is obtained by keeping the first and the last letter and putting in between the number of letters omitted: K, then eight letters (u, b, e, r, n, e, t, e), then s. Whoever does not like it can pronounce the full name (\emph{coo-ber-net-ees}, also when it is shortened as k8s).
\end{notebox}

Kubernetes derives from platforms developed by Google (Borg and Omega), and being directly backed by Google is part of the reason why it became so powerful and successful. The slides also list the following characteristics: it is designed to be composable, it is more complex than some others, it scales to thousands of machines, it had a very rapid adoption and it has a large community of thousands of developers. Even more than for Docker, technical information is required to understand how it works in practice: that is why the laboratory activity on Kubernetes is important.

The study of Kubernetes has two goals. The first, and the most crucial, is to understand at high level its \emph{architecture}. It is quite complex and very peculiar: with Docker Swarm there is one software running on the Docker host and all the containers run on the same machine managed by it, whereas Kubernetes introduces many extra terms and extra actors that are not found in any other container orchestration. The architecture is \emph{modular}, and it is useful to see how its actors map to what is already known about Docker creation, management and deployment. The second goal is to see the main goals that Kubernetes, as an orchestrator for cloud computing, is able to achieve, most of which have already been mentioned: it is a systematization of knowledge already acquired.

\subsection{Cluster model}

A Kubernetes system is organized as a \emph{cluster} composed of multiple \emph{nodes}. Each node represents a compute host, which may be a physical machine or a virtual machine. This is already different with respect to other platforms: in Kubernetes the set of compute hosts may be full virtual machines (not containers) or traditional physical hosts. Cluster operations are typically managed via kubectl, a command-line interface that communicates with the Kubernetes API.

\begin{center}
	\safeimg[width=5in]{media/image179.png}
\end{center}

A cluster logically separates:

\begin{itemize}
\item a \textbf{control plane} that exposes the API and coordinates global decisions such as scheduling. It runs on one node of the cluster, the \textbf{master node}: a sort of brain of the platform that manages all the nodes of that cluster;
\item and \textbf{worker nodes} that run application workloads. By themselves they do not provide extra intelligence: they are in charge of executing the commands that come from the control plane, that is, from the master node.
\end{itemize}

The figure shows, on the left, one master node (a physical computer or a virtual machine) and three worker nodes (physical computers, virtual machines or a combination of them). The user does \emph{not} interact directly with the worker nodes, but only with the master node, typically with the command line tool \texttt{kubectl}, which gives access to the Kubernetes API server running on the master node.

A data center may host \emph{multiple clusters}, each with its single master node and multiple worker nodes, and, if desired, a top-level orchestrator that provides decisions to the local clusters.

\subsection{Control plane responsibilities}

The control plane oversees nodes and manages workload scheduling. It maintains cluster state and drives the actual system towards a desired state specified by users. All the decisions about the scheduling, activation and stop of containers are taken at the level of the master node, but they are implemented by the worker nodes.

The control plane commonly includes:

\begin{itemize}
\item \textbf{API server (kube-apiserver)}: the front-end that exposes the Kubernetes API. It accepts the requests of the user, interacts with the other modules of the same master node and gives commands to the worker nodes. The name may recall the API gateway seen for microservices, but it covers a different role.
\item \textbf{State store (etcd)}: a key-value (database) service that holds the cluster state, keeping track of the current state of the whole cluster.
\item \textbf{Scheduler (kube-scheduler)}: the software that understands which is the best compute host, among the worker nodes, on which a container requested by a user should be activated, and assigns pods to nodes based on constraints and available resources. It may adopt different scheduling algorithms, for example giving priority to the compute host on which fewer resources have been used, or trying to put containers with many communication requirements on the same host, to avoid many communications over the internal network. Since the architecture is modular, a developer can extend the scheduler of the master node with a custom scheduling algorithm without modifying any other part. When a new container must be instantiated, the API server interacts with the scheduler to find the best compute host.
\item \textbf{Controllers (controller manager)}: reconcile the actual state with the desired state by continuously observing resources and taking actions. The controller manager oversees the life cycle of all the containers already activated and requests the modifications from the worker nodes when needed. If a container fails, it notices it, updates the status and requests, through the API server, the activation of a new replacing container.
\item \textbf{Cloud controller manager} (optional): a more user-friendly interface to oversee everything when one does not want to use only \texttt{kubectl} to interact with the API server. It is not mandatory and not the main element of the architecture: it serves user friendliness more than functionality.
\end{itemize}

\begin{center}
	\safeimg[width=3.6in]{media/image181.png}
\end{center}

Conceptually, users and automation systems interact with the API server. The scheduler and controllers act on the resulting desired state, while nodes report status back to the control plane. In the figure of the master node the API server interacts with every other element: there is no direct communication between two other elements without the intermediation of the API server itself.

\subsection{Node agents and runtime}

Worker nodes run agent processes that implement the control plane directives. There must be a way of interaction between the API server of the master node and the worker nodes.

\begin{itemize}
\item \textbf{Kubelet}: runs on each worker node, communicates with the API server of the master node, receives requests (pod specifications), ensures the corresponding containers are running, and sends the final reply to the API server. It also provides the telemetry information about the status of the single worker node, so that the controller manager can take global decisions with a comprehensive view of the whole cluster.
\item \textbf{Kube-proxy}: runs on each worker node. On the one hand, it takes control of the life cycle of the containers within the single worker node, so that they cannot interfere with the others; on the other hand, it configures some security-oriented parameters such as the network policies, that define which containers can communicate with which others, and manages network rules on the host to implement service networking abstractions.
\item \textbf{Container runtime}: a service that allows the creation and destruction of containers, preferably present on each worker node. Historically Docker was widely used, and Kubernetes supports multiple runtimes. In this role the \emph{Docker daemon} is a worker process that runs containers every time it gets commands from the master node. Docker Swarm would be redundant here, because the orchestration is already provided by the modular components of the master node. The instructions that earlier came from the user (when only Docker was discussed) now come from the API server: the scheduler decides where to put each container, the API server creates the request and sends it to the kubelet, and the kubelet sends it to the Docker daemon of that node.
\end{itemize}

\section{Kubernetes object model}

Kubernetes represents workloads and configuration as objects. Users define objects in a declarative format, and the system attempts to realize the declared state.

\begin{notebox}
	\textbf{Imperative versus declarative languages.} In an \emph{imperative} language the full course of action that should be performed to reach a goal has to be specified. For example, in security: ``block port 80 for the server hosted at the IP address 130.192.10.1'' would require installing a firewall (a packet filter) in the middlebox connected to the gateway of the subnetwork, giving all the information on the addresses and also providing the configuration of this packet filter. In a \emph{declarative} language the same command is just ``I want to achieve the goal of blocking this port for that server'', without specifying how the goal is achieved.

	\medskip
	Kubernetes follows the declarative philosophy: whenever pods, containers or deployments are wanted, declarative files are created that only state the goals, and the different elements of the master node, in collaboration among them, decide the best course of action for the specific platform.
\end{notebox}

\subsection{Pods}

A \emph{pod} is the basic execution unit of a Kubernetes application. It is the smallest and simplest object in the Kubernetes model that can be created and deployed: the basic execution unit of any application running on a worker node. A pod contains one or more containers that cooperate to perform a function and that share certain resources.

By the definition of the Kubernetes standard, a pod is one container \emph{or} a group of containers serving the same functionality (for example providing load balancing among them), so it would be incorrect to say that a pod is one container. In reality, however, for simplicity and to ease the management of the clusters, in the majority of cases (roughly 90--95\%) a pod corresponds to a single container.

\end{center}

Key properties of pods include:

\begin{itemize}
\item \textbf{Single-node placement}: a pod is scheduled to exactly one node and its containers run on that node. This is a strict requirement, whatever the pod is: if a pod is made of three containers, they cannot be split among different worker nodes, and a single container cannot use the CPU of one compute host and the memory of another. In the figure there are two worker nodes governed by the master node, each with two pods of two containers each, and no pod crosses two worker nodes.
\item \textbf{Shared context}: containers in a pod can share network identity and storage volumes, enabling sidecar patterns such as log shipping or proxying.
\item \textbf{Process analogy}: a pod plays a role analogous to a process in an operating system, in the sense that it is the unit scheduled by the system and represents a running workload instance.
\end{itemize}

The following YAML specification illustrates a simple pod running an nginx container, exposing a port and mounting an ephemeral volume for logs. The only thing specified is how the pod must be structured: a pod corresponding to the nginx-based image, whose container listens on the port 8080 with TCP as transport protocol (and HTTP as application protocol).

\begin{codeblock}
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  namespace: default
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx
      ports:
        - name: http
          containerPort: 8080
          protocol: TCP
      volumeMounts:
        - name: logs
          mountPath: /var/log/
  volumes:
    - name: logs
      emptyDir: {}
\end{codeblock}

The field containerPort: 8080 indicates that the container listens on port 8080 for TCP traffic.

This definition of a pod is, however, a \emph{passive} definition: it does not request the instantiation of the pod. It only says that pods of this type, named nginx and with this label, use the image (like a Docker image) written in the \texttt{spec: containers} part of the file.

\subsection{Deployments}

To \emph{instantiate} pods another Kubernetes resource is needed: the deployment. Pods are typically managed by higher-level controllers. A \emph{Deployment}, a YAML declarative file, is used to roll out pods based on the goals and requests of the user: it declares a desired state for a replicated set of pods, such as running a fixed number of replicas of an application. The deployment controller then creates and updates pod replicas to converge to the desired state.

A deployment supports:

\begin{itemize}
\item \textbf{Replica management}: maintaining a specified number of replicas.
\item \textbf{Rolling updates}: gradually replacing old replicas with new ones to avoid downtime.
\item \textbf{Rollback}: returning to a previous version if a rollout fails.
\item \textbf{Pause and resume}: controlling the progress of updates.
\end{itemize}

The following YAML specification illustrates a deployment of three replicas of an nginx container: the user creates a resource named nginx-deployment whose goal is to replicate three times, that is, to instantiate three containers for the pod named nginx defined in the previous file.

\begin{codeblock}
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.14.2
          ports:
            - containerPort: 8080
\end{codeblock}

In this specification, the selector matches pods labeled app: nginx. The template describes the pod to be replicated.

Note that there is no specification of which worker nodes must host these containers, nor of how or when they must be activated: all these decisions are left to the master node. The controller of the master node tries to reach the goal as soon as possible, understanding the current situation of the cluster and scheduling the containers in order to meet all the requirements and goals specified in the declarative file.

\subsection{Services}

After the pods are rolled out through deployments, they do not have, by default, an IP address by means of which they can be reached. To make them reachable (also from the outside) addresses must be assigned, and this is done by creating another Kubernetes resource, the \emph{Service}. The term is used in a peculiar way with respect to application development: a service is a resource that groups similar deployed pods so that they receive traffic under the same name or the same IP address. In general services are created together with deployments: the pods are rolled out and then they are allowed to receive traffic with a service. Their main goals are to assign IP addresses (also static ones) and to configure load balancing.

A \emph{Service} provides a stable network endpoint for a set of pods. Because pods are ephemeral and their IP addresses can change when they are rescheduled, services decouple clients from pod identities. A service selects pods using labels and can implement load balancing across the selected pods.

Services commonly provide:

\begin{itemize}
\item a stable virtual IP address within the cluster,
\item a DNS name that resolves to the service endpoint,
\item load balancing among pod backends.
\end{itemize}

The following YAML specification illustrates a cluster-internal service that targets pods labeled app: nginx. It is a \emph{ClusterIP} service, which does not provide load balancing by itself but simply provides an IP address: all the containers that match the selector are reachable with the IP address 10.96.0.100. It is just a resource that enables a pod, a group of containers, to receive traffic under a specific IP address.

\begin{codeblock}
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  selector:
    app: nginx
  type: ClusterIP
  clusterIP: 10.96.0.100
  ports:
    - protocol: TCP
      port: 8080
      targetPort: 80
\end{codeblock}

In this example, the service uses the cluster-internal IP address 10.96.0.100. The service receives TCP traffic on port 8080 and forwards it to port 80 on the selected pods.

Pods, deployments and services are managed on the worker nodes by the \emph{kubelet}, which communicates with the Kubernetes API server of the master node and gets the requests, and by a container runtime such as the Docker daemon process, which activates, stops and scales the containers as needed.

\section{Network policy}

Each worker node also runs a kube-proxy which, among its tasks, manages the \emph{network rules} of that node. Network rules are comparable to firewall rules: their goal is to establish whether a certain communication involving that worker node is allowed or not. In Kubernetes these network rules are called network policies.

Kubernetes provides a \emph{NetworkPolicy} object to implement network access control between pods. A network policy specifies allowed flows by describing selectors and layer 3 and layer 4 parameters. Traffic can be blocked in different ways: one may specify a 5-tuple as in a normal packet filter, but in most cases the source or destination of an enabled or blocked communication is expressed with the \emph{labels} put in the previous files (for example the nginx service label or the nginx deployment label), so that low-level configuration parameters such as IP addresses are avoided and everything stays at a higher level.

A policy typically:

\begin{itemize}
\item selects a set of pods to which the policy applies using label selectors,
\item specifies ingress rules that allow traffic to the selected pods from certain sources,
\item specifies egress rules that allow traffic from the selected pods to certain destinations,
\item may also include namespace selectors to scope rules across namespaces.
\end{itemize}

Network policies form a declarative firewall mechanism. Their enforcement depends on the cluster networking implementation supporting policy evaluation.

	\textbf{Security and labs.} Network policies are a way to filter traffic, so they concern security and will be studied in more detail in the second semester, which includes one laboratory activity entirely focused on them. In the first semester the laboratory activities practice the basic entities seen above (pods, deployments, services, etc.), whereas in the second semester the students will also modify the way the different actors interact by configuring Kubernetes network policies.

\section{Core orchestration functions in Kubernetes}

Kubernetes schedules and automates container-related tasks throughout the application lifecycle. Given the services running on the master node, the main goals it achieves are: rolling deployments, service discovery, load balancing, health checking, cluster networking, autoscaling and declarative configuration. Almost all these terms are already known from the previous lectures; they are reviewed here for the last time, since this is the last theoretical topic on containerization and, in general, on virtualization before moving to the next part of the course.

\subsection{Rolling deployments}

A deployment defines the desired number of replicas and the pod template for an application. Kubernetes automatically rolls out containers based on the declarative YAML file of the deployment without requiring any extra information from the user: the master node only gets the desired state and, supported by the controllers and by the scheduler, reaches this state as soon as possible and in the best possible way. A \emph{rollout} is a controlled change to the deployment, often involving a new container image version. Kubernetes performs rollouts incrementally, for example by creating new pods one at a time, verifying their health, and then terminating old pods.

Deployments can be stopped, if the controller notices that they impact the behavior of the cluster or if the user requests it with \texttt{kubectl}, and they can be put in a frozen state and resumed when possible. This is possible because the control plane has a complete view of the whole cluster, keeps track of how the state of the worker nodes evolves and can continuously decide to send new requests to them.

Zero-downtime updates can be achieved by ensuring that sufficient healthy replicas remain available while new replicas are created. Rollouts can be paused, resumed, and rolled back. A common alternative strategy is a \emph{blue-green} deployment in which two versions run simultaneously and traffic is switched to the new version once it is stable.

\begin{notebox}
	\textbf{Blue-green deployment, in detail.} Suppose an application has been updated and the existing container must be upgraded with a new one. A simple possibility is to kill the first container and then execute the new one, but this causes a period of disservice in which the new container is not yet available. With a blue-green deployment the previous container is kept as it was instantiated and the new one is created. When the new one is up, the previous is \emph{not} killed immediately: the control plane starts to send instructions from the API server to the kubelets of the worker nodes, informing them to redirect the traffic \emph{part by part} to the new instance. The two instances coexist for a certain period, and only when all the traffic has been successfully moved to the new instance, and the controllers have verified that the new instance works as expected, is the original one killed.

	\medskip
	A human could do this manually, but not easily at such a big scale: the control plane completely abstracts this operation away from the users and provides very high scalability for it. Deployments are in this sense even more intelligent than what can be done with simple scripts.
\end{notebox}

\subsection{Service discovery}

Applications running in a cluster require mechanisms to locate other services. In Kubernetes any entity (any container, pod or service) can find the other applications deployed in the cluster automatically, even without knowing their IP addresses. Kubernetes supports service discovery through DNS and, in some environments, through injected environment variables. A service name is resolved to a stable endpoint, enabling clients to depend on logical service identities rather than on changing pod addresses.

The implementation may be an internal DNS or another ad hoc mechanism created for the cluster, such as local environment variables that map names to IP addresses and can be easily interrogated by any container. This is not something expected from a normal orchestrator, since the containers could be expected to interact with an external DNS cache in the local area network outside the cluster; but that would be redundant, as it requires interacting with an external element. Here the DNS or the ad hoc mechanism is implemented within the cluster, so the interrogation is done by a worker node towards another element of the architecture (possibly another worker node), and the information is then used to perform the communication.

\subsection{Load balancing}

When a service selects multiple pod replicas, traffic must be distributed among them. Kubernetes supports load balancing at the service level within the cluster, and it can integrate with external load balancers provided by the underlying infrastructure. In particular there is a service of type \emph{load balancer} that manages the distribution of the requests to the containers (pods) created with the same label, perhaps within the same deployment. No explicit configuration parameters are required from the user: it is managed automatically by the control plane thanks to the support of the controllers.

The service abstraction enables both internal and external request distribution.

\subsection{Health checking and self-healing}

High availability requires detecting failed or unhealthy containers and replacing them. Kubernetes provides probing mechanisms to assess container health. When a container fails or does not meet health requirements, Kubernetes can restart it or replace its pod instance, thereby reducing downtime.

For example, if the goal declared in a deployment is five containers, five are created and one of them fails, the master node notices that the goal is no longer satisfied and, without informing the user or asking for authorization, immediately activates a new one, minimizing the downtime. This is possible because there is no human intervention: the Kubernetes controllers send the requests directly to the worker nodes through the kube API server.

\subsection{Cluster networking}

Cluster networking connects pods across machines and manages address assignment. Kubernetes networking aims to provide a model in which each pod can communicate with other pods without network address translation, subject to policies and topology. Implementations provide mechanisms for IP management, routing, and integration with services.

Through the network policies it can be specified that the containers or pods of one cluster may communicate with the ones of another cluster, or that, within the same cluster, only pairs selected in a specific way may communicate while all the others are forbidden. It is a way of creating \emph{virtual networking}, establishing how the different containers can communicate with each other without needing someone from the outside to provide such restrictions or allowances.

\subsection{Autoscaling}

As load increases, more pod replicas may be required to maintain performance. Kubernetes supports autoscaling by monitoring metrics such as CPU and memory usage and by using user-defined telemetry. Based on configured policies, the system increases or decreases the number of replicas: the controllers of the master node understand when more instances are needed, if they have been configured to scale depending on the volume of requests, and automatically increase or decrease the number of running containers.

Autoscaling can also apply to cluster resources, where node counts are adjusted to improve utilization or to accommodate increased workload demand. It perfectly suits the \emph{on-demand} usage characteristic of cloud computing, one of the first discussed at the beginning of the cloud computing part, thus closing the loop in a certain way.

\subsection{Declarative configuration}

A central design principle of Kubernetes is \emph{declarative configuration}. Users declare a desired state (for example four running replicas of a web server) in configuration files, specifying only the final goal, and the system continuously acts to achieve and maintain that state by interacting with all the modular elements of its architecture.

Declarative configuration contrasts with imperative approaches where operators specify sequences of actions to produce a state. Imperative procedures can be error-prone and can complicate rollback because the system state depends on the exact history of executed actions. With declarative configuration, the desired state is the primary artifact, and reconciliation logic aims to make the actual state match it.
