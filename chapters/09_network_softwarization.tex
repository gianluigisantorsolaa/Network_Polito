\chapter{Network Softwarization}

\section{From physical to virtual networks}

The first part of the course dealt with advanced topics in computer networking, that is, with the different ways in which computer networks can be managed. The second part was dedicated to cloud computing and, within it, to the virtualization techniques that make it possible, from traditional virtualization up to containerization. \emph{Network softwarization} combines these two aspects: the goal is no longer to have physical networks, but \emph{virtual} networks, in which the different aspects of network management are addressed through virtualization.

Network softwarization is a quite recent topic. Most of the proposals, technologies and standards discussed in this chapter were defined starting from around 2010, that is, at the beginning of the previous decade, and are therefore considerably more recent than most of the other topics of the course.

Two main paradigms enable network softwarization. They are not one the replacement of the other: they are \emph{complementary}, because they serve different purposes and are therefore based on completely different mechanisms.

\begin{itemize}
\item \textbf{SDN} (\emph{Software Defined Networking}) provides an \emph{abstraction for the operation of forwarding}. Forwarding is no longer performed only by normal routers on their own: they rely on the support of external software, which understands the best way to reach a certain destination.
\item \textbf{NFV} (\emph{Network Functions Virtualization}) aims at \emph{virtualizing the way network functions compute their decisions}. The network functions themselves are no longer instantiated as physical middleboxes, but as virtual machines or containers deployed on general-purpose servers.
\end{itemize}

\section{Software-Defined Networking (SDN)}

\subsection{Background: management, control and data plane}

To understand why SDN was introduced, and later how it works with its main pillars, it is useful to recall how network functions are typically structured from the architectural point of view. The different functionalities, the different tasks that a network function may perform, can be classified into three groups, called \emph{planes}: the \emph{management plane}, the \emph{control plane} and the \emph{data plane}.

\begin{center}
	\safeimg[width=5in]{media/image182.png}
\end{center}

\begin{itemize}
\item \textbf{Data plane}: forwarding. The action is not an intelligent operation: it is simply the application of a normal algorithm to data that is already available, such as a routing table or a filtering database.
\item \textbf{Control plane}: the dynamic configuration of the data plane tables (for example routing with OSPF). These are the operations that should have more intelligence, because they must create all the data structures that the operations of the data plane will use later to take their decisions. If the data plane works on routing tables or filtering databases, the control plane is composed of the protocols that write those data structures.
\item \textbf{Management plane}: the configuration made by the user or the administrator. These operations are not strictly related to the management of data, but to the management of the network function itself: they establish how the function should work, through APIs or a graphical user interface, if the middlebox offers one.
\end{itemize}

The interaction between control plane and data plane always involves the \emph{sharing of some data}, which is typically stored in tables: the control plane writes them and the data plane reads them.

\begin{notebox}
	\textbf{An IP router.} A router applies a forwarding algorithm that reads the routing table and decides the next hop of a received packet, based on its destination IP address and on the content of the table; typically it uses the \emph{longest prefix match} algorithm (data plane). It also writes the routing tables themselves, by interacting with the other routers through routing protocols such as BGP, RIP and OSPF (control plane). Finally, it may offer APIs by means of which an administrator, a human user or an external orchestrator, can configure its behavior (management plane).

	\medskip
	\textbf{An Ethernet switch.} A switch has forwarding algorithms that look at its filtering database (data plane), an algorithm that automatically populates this database, the \emph{backward learning} algorithm (control plane), and a way for a user to interact with it remotely, for example through SSH, in order to configure it (management plane).
\end{notebox}

Traditionally, when a network function such as a Cisco router is bought, it implements operations of all three planes: a ``stupid'' forwarding algorithm that just looks at data, a very diligent control plane algorithm (an instance of a routing protocol that writes the data structures) and some APIs that support the management by the users.

\subsection{The original definition of SDN}

In SDN the main idea has been to break this paradigm, which lasted for many years, of having all the planes within a single middlebox. Engineers started to think that it may be \emph{redundant}, because everything has to be replicated and, above all, the control plane has to be replicated in all the devices. It may also be \emph{expensive}: if 100 routers are needed just to do forwarding, 100 routers must be bought for their capabilities even though perhaps nothing about the control plane is needed.

A possible way to proceed is therefore to \emph{separate the planes}: some devices are only responsible for the operations of the data plane, and other devices are only responsible for the operations of the control plane. The management plane is kept aside, because it is a bit peculiar and it is not addressed in these lectures.

\begin{center}
	\safeimg[width=4in]{media/image183.png}
\end{center}

The original definition of SDN is therefore the following: a new network paradigm that \emph{physically separates} the control plane from the forwarding plane, and where a control plane can \emph{programmatically} control several devices. A network based on this principle is no longer composed of middleboxes that have both data plane and control plane operations. Instead:

\begin{itemize}
\item some middleboxes only do forwarding, and take their decisions on data structures written by other elements. The functions in charge of the data plane are typically \emph{physical} middleboxes, so even in SDN there is still hardware responsible for forwarding. They are called \textbf{SDN switches}, or programmable switches;
\item the control plane is \emph{virtualized}: it is managed by a process that instantiates some orchestration software, the \textbf{SDN controller}. The controller is a \emph{single} element, a software, that programmatically writes and controls the forwarding tables of the SDN switches. It should have a comprehensive view of the physical network and it creates the tables of all the programmable switches, so that they can use them to take a forwarding decision for each received packet.
\end{itemize}

In a traditional network each router or switch is composed of both a data plane and a control plane; in an SDN network there is a clear separation. In this way the network designer does not have to buy many routers, which may be quite expensive: it is enough to buy very simple \emph{white label} switches, which are ``stupid'' because all they implement is an algorithm that reads a table and makes forwarding decisions, plus a separate server on which the software of the SDN controller is installed. This software automatically interacts with all the SDN switches.

\begin{notebox}
	\textbf{SDN and automation.} SDN was also the first way to bring \emph{automation} to computer networks. In cloud computing automation was introduced with orchestrators such as the ones that manage Docker containers (Docker Swarm, Kubernetes); almost in the same years, around 2010, in networks the orchestration was introduced with the concept of SDN controller. The controller is a de facto orchestrator, because it checks how the different programmable switches work and may automatically alter their behavior.
\end{notebox}

When a human user wants to interact with the network, the user interacts with the SDN controller. The controller therefore also offers some API or interface towards the user, as part of a management plane, to establish how the controller should work and, consequently, how it will configure the SDN switches.

Moreover, since the controller is software, everyone may write their own controller, or search repositories for controllers that are already available. Another advantage is therefore a reduced \emph{lock-in} with specific vendors: simple programmable switches are the same for everyone, so a vendor cannot add more features to them than the others. The controller software, stored on a general-purpose server, may be proprietary but is most often free and open, so both expenses and lock-in are reduced.

\subsection{The intelligence is in the controller}

SDN is not just a new layer on top of existing routers: it reorganizes the network architecture by moving some functions to other places. The controller (distributed or centralized) keeps the intelligence, and routers become simpler, cheaper and faster.

The way SDN works is simple, because it is based only on the idea of separating control and data plane. In this separation the distributed architecture of the switches should be \emph{as simple as possible}, whereas every time a complex decision is needed, it must be put in the code of the SDN controller. The controller keeps the whole intelligence of the network, as if it were a single administrator with a complete overview of the entire network. This is possible because the controller interacts with all the very simple SDN switches and takes its decisions on the basis of the data they simply provide. The switches can at most provide data to the controller: they cannot order the controller to do something, they only have to be subject to the decisions it takes.

\subsection{The three SDN pillars (plus one)}

When SDN was originally standardized, some pillars, some building blocks of any SDN-based network, were defined. They are three.

\begin{enumerate}
\item \textbf{Separate the control plane from the data plane}, from the physical point of view. The SDN controller cannot run on an SDN switch: it is not possible to take one SDN switch and make it the controller of all the others. It must be a separate physical element running some software.
\item \textbf{Simple data plane} (``plumbing''). The data plane should be as simple as possible, and all the intelligent decisions should be placed in the control plane.
\item \textbf{Centralized control}, \emph{at least logically}. Only one entity oversees all the SDN switches of the data plane. As will be seen later, a distributed controller is also possible, but from the logical point of view its different instances must work as if they were a single one.
\end{enumerate}

\begin{notebox}
	\textbf{When is a network SDN?} If a network satisfies these three characteristics (separation of data and control plane, simplicity of the data plane and control centralization, at least logically) it can already be called an SDN-compliant, or SDN-aware, network.
\end{notebox}

\subsubsection*{A fourth, de facto pillar: context-based forwarding}
\addcontentsline{toc}{subsubsection}{A fourth, de facto pillar: context-based forwarding}

When the first implementations of the paradigm were created, they added new features, as usual. Among them, one was deemed so important and so impactful that today it has become almost a synonym of SDN, a \emph{fourth de facto pillar}: \textbf{context-based forwarding}, introduced for the first time by the \textbf{OpenFlow} protocol. Its idea is that the controller does not need to take all the decisions at the beginning: it may take them \emph{on the fly}, based on the context of the network, that is, on the current status of the network and on how the switches have behaved in the past. This pillar was not originally envisioned when SDN was first defined in its document, but today it is considered almost as important as the others. It is discussed in detail later.

\subsection{Pillar 1: separation of control plane and data plane}

The data plane is implemented with very simple packet forwarding hardware, the SDN switches, which contain \emph{lookup tables}: the equivalents of routing tables and filtering databases are embedded in hardware in the SDN switches. The control plane is instead placed on a physical \emph{server} running the SDN controller. The controller may be enriched with the software one wants for the \emph{routing logic}. The overall software may be composed of two separate modules: a sub-module only for the controlling, that is, for the interface with the switches, and another one that takes the routing decisions. The software with the routing logic communicates its decisions to the SDN controller, and the SDN controller communicates them to the SDN switches.

\subsubsection*{Northbound and southbound interfaces}
\addcontentsline{toc}{subsubsection}{Northbound and southbound interfaces}

A physical separation creates a gap that must be filled. The same happened with microservices: at the beginning there was a single process and everything was done internally; with microservices the different parts have to communicate with each other to provide the overall service. Here too, new APIs and new protocols were needed, to allow the different elements of this distributed network to communicate. On the host in which the SDN controller runs there are two main interfaces (some others are discussed later):

\begin{itemize}
\item the \textbf{northbound interface}, most often based on REST APIs, which allows users or other pieces of software to interact with the system;
\item the \textbf{southbound interface}, through which controller and switches communicate with each other.
\end{itemize}

When SDN was first proposed, the main focus was on the southbound interface, because all the elements communicating through it were novel. Different protocols that establish the messages exchanged between server and SDN switches were defined. One of the first was the \textbf{OpenFlow} protocol, which was created for this communication but then became almost a synonym of the idea of separation between control plane and data plane.

\begin{notebox}
	\textbf{Switches do not talk to each other.} At most, SDN switches communicate with the controller, for example by sending some statistics about the traffic they inspect. They do not provide information to one another. This is completely different from what happens with IP routers, which exchange routing information to build their routing tables and to have a shared view of the whole network. SDN switches do \emph{not} have a comprehensive view of the network: they only read data structures written by the controller, without understanding anything about them.
\end{notebox}

\subsubsection*{Advantages of the separation}
\addcontentsline{toc}{subsubsection}{Advantages of the separation}

\paragraph{Control plane.} Maintainability and the ease of modifying the behavior of the controller are the main reasons why SDN became popular. The routing logic is easy to change: new applications can be executed, replacing the original routing logic with more sophisticated algorithms.

Consider an IP network, and a research team of a company that wants to change the way forwarding is done, because it does not want to use the longest prefix match any more and wants to test other forwarding algorithms. One possibility is \emph{MPLS} (Multi-Protocol Label Switching), whose idea is that forwarding should not be based on destination IP addresses, but on labels, numbers placed within the packets. Another is a new network layer protocol with a new kind of routing, closer to \emph{ATM}, an alternative to IP based on the idea of connection: before a communication starts, the peers reserve all the resources for the connection along all the routers.

With a hardware network, the only way to move from one type of network to another is to trash the IP routers, of Cisco or of any other vendor, and buy completely new devices working in different ways, because each one works on different principles. With SDN all the switches are ``stupid'': they only read a table, so what really matters is \emph{the way the table is written}. The semantics of the table can be altered, because it is written by the controller. The sequence is the following:

\begin{enumerate}
\item the controller is associated with routing logic 1, the IP routing logic, which was used to populate all the forwarding tables of the switches;
\item the controller is associated with a second routing logic, which creates the new forwarding tables (in the example of the figure, seven switches, so seven new tables). They are \emph{not} pushed immediately;
\item in the meantime the switches \emph{continue to work with the previous tables}, those based on routing logic 1. With physical devices, instead, the routers would be down while they are dismantled and replaced, and the network would suffer a complete disservice;
\item only when all the tables are ready they are pushed to the switches, through protocols such as OpenFlow, potentially in parallel.
\end{enumerate}

There is of course a very small delay for pushing the tables, in the order of one second or a few seconds, much less than the hours of disservice needed to dismantle a network, install a new one, activate the new routing protocol instances and let the routers synchronize their routing tables. It is much faster also because everything is done in software: nothing is touched in the hardware, only the routing logic attached to the controller is modified.

The network may even have \emph{multiple routing logics at the same time}: for example, the left part of the network may work with the IP routing logic and the right part with a new label-based logic (a \emph{sliced} network). The controller knows this, creates the forwarding tables of the left switches for the first logic and those of the right switches for the second one, and pushes them. The switches are not aware of it: they receive the tables and read them, without knowing that they were created with completely different logics. The slides also mention a third example, the separation of a research network from a production network.

\begin{notebox}
	\textbf{Do the switches communicate with each other?} No. They only get the tables from the controller and read them to understand how to forward packets, without exchanging any information. If a packet has to go from a switch on the left to a switch on the right, it is the \emph{controller} that decides: it has the complete overview of the network and chooses the best path according to its logic, so everything is decided by the controller. The switches can only provide it with information about the network and then wait for its decisions.
\end{notebox}

\paragraph{Data plane.} The advantages are not limited to the control plane. The switches are simple, so they are \emph{faster}: they have no extra overhead due to the control and the management plane, they just wait for the decisions and enforce them. Since they are all simple and equal, they are also really \emph{cheap}, and no vendor can claim that its SDN switch is more powerful than the others: all of them are identical and only apply forwarding algorithms. It is therefore easy to replace one vendor with another, and many southbound protocols are \emph{standard}, hence applicable to any SDN switch: the standard southbound interface guarantees interoperability.

\subsection{Pillar 2: simple data plane (``plumbing'')}

The second pillar is the simplicity of the data plane, also called \emph{plumbing}. The picture of pipes on the slide is the hint: the data plane is just a sequence of interconnections that can be seen as pipes. Once a pipe has been installed, it simply lets water flow through it, but the direction of the water is established at the moment of installation. Likewise, the controller installs the ``pipes'' and the switches simply forward traffic according to the way they were attached to each other. All of this is possible thanks to the forwarding tables stored in the switches and written by the controller.

\begin{center}
	\safeimg[width=5in]{media/image185.png}
\end{center}

The data plane mainly performs traffic forwarding, based on the \emph{match/action} paradigm: each rule has a condition on some fields (the match) and an action. The two most used actions are:

\begin{itemize}
\item \textbf{forward}: send the packets that satisfy the condition to a given port (or ports);
\item \textbf{drop}: block the traffic.
\end{itemize}

The \emph{drop} action is interesting because it can be used as a form of \emph{filtering}: SDN switches also work as very simple filters, deciding that a packet must be blocked explicitly, because a rule contains a drop action, and not just by exclusion. More powerful actions may be defined and are seen later.

The same flexibility holds for the conditions of the rules, which may consider different header fields:

For a custom logic one has to create the corresponding routing logic in the controller, but from the point of view of the switches nothing changes: they just look at those fields. If later the logic is enriched with other fields, a new routing logic is created and the switches are already compliant, because they can read almost all the fields available in any received packet.

\subsection{Pillar 3: centralized control}

The third pillar is the centralization of the control plane, at least from the logical point of view. Centralization is a prerequisite: without a comprehensive view of the entire network the controller cannot establish the forwarding tables of all the switches. In a \emph{distributed} routing protocol each router can compute its own routing table because, in a way, it has a comprehensive view of the network thanks to the information coming from the other routers (current routing protocols operate on each node in isolation). In SDN, instead, the decisions are centralized and based on the information that the controller receives from the switches: it knows how each switch is connected to the others, reconstructs the full picture of the network and computes the forwarding tables of all the switches. Centralized control is usually easier than distributed control, and the software can easily control the entire network.

Through its northbound interface, towards users and external software, the controller may offer \emph{different visibilities} of the structure of the network:

\begin{itemize}
\item the \textbf{full network topology}: the user knows how the switches are interconnected;
\item a more limited and controlled view, the \textbf{big switch abstraction}.
\end{itemize}

\subsubsection*{The big switch abstraction}
\addcontentsline{toc}{subsubsection}{The big switch abstraction}

Consider an SDN network with several edge ports, say P1 to P5, through which packets enter the network. Each port may be connected to another, separate network: a subnetwork of a company, a data center, and so on. If one is in charge of these subnetworks, one does not really care about the way packets cross the intermediate SDN-based network. One may just want to specify, for example, that the subnetwork connected to P1 can communicate with the one connected to P5, and that the subnetwork of P4 can communicate with P2 and P3.

\begin{center}
	\safeimg[width=3in]{media/image186.png}
\end{center}

In this scenario, when there is no need to know the topology, the controller may export a \emph{control view} of the network: for a user application, acting as a management plane, the whole network appears as \emph{a single big switch} with five ports. The user states ``I want communication from 1 to 5, and from 2 to 3 and 4'' (or the opposite, blocking some communications, since SDN switches can also drop packets) and the controller internally finds the best path according to its routing logic and creates the forwarding tables. The user knows nothing about this, and does not need to: the only purpose was to enable (or block) those communications.

The abstraction hides the internal details of the network and lets the software issue high-level commands, often called \emph{intents}, for example:

\begin{itemize}
\item set a given configuration on all the \emph{edge} ports;
\item create a direct, circuit-like path \emph{from port A to port B}. The controller sets up the path, for instance through a chain of VLANs.
\end{itemize}

The software can use either the normal view, which offers visibility of the internals of the network, or the big switch view.

\begin{notebox}
	\textbf{Privacy.} The big switch abstraction is also useful in terms of privacy: a provider that manages an SDN-based network does not have to give complete information about its structure to the users, the customers. It just provides information about the \emph{access points}, and the users decide how the networks connected to those access points should, and can, interact with each other.
\end{notebox}

\subsection{Intent-based networking and policy-based management}

The big switch abstraction is an element of another paradigm which, in the last fifteen years, has become fundamental for network management. It is not addressed in this course, but is mentioned to give an idea of it. Depending on the scenario it is called \textbf{IBN}, \emph{Intent-Based Networking}, or \textbf{PBM}, \emph{Policy-Based Management}; applied specifically to networks it is \textbf{PBNM}, \emph{Policy-Based Network Management}.

The main concept is that a human user should only specify \emph{high-level intents} or \emph{high-level policies}, which express goals, such as allowing a communication or blocking another one, \emph{without caring about the course of action} by which they are resolved. In the big switch example, the user does not care about the exact path that allows a communication: he or she only says ``I want a communication''. This recalls the \emph{declarative configuration} of Kubernetes seen in the previous chapter: IBN and PBNM bring that paradigm to computer networks.

In the literature, and at conferences, some authors state that intents and policies are completely different things (intents should be written in natural language, or should be just goals, whereas policies should already hint at the course of action), while others consider them almost the same. What matters is that high-level sentences, written in natural language or in predefined languages based on templates, are \emph{automatically converted into real configurations} by a piece of software such as the SDN controller.

\begin{notebox}
	\textbf{The same idea in network security.} Consider a firewall. In the lab activity the iptables firewall was configured by writing low-level rules by hand, knowing the exact syntax. With IBN or PBNM one only writes a sentence such as ``this source cannot communicate with this destination'', perhaps using labels instead of IP addresses, and without any firewall-specific language. The statement, a policy or an intent, is given to a software, an orchestrator or a controller, that performs a \emph{refinement}: through refinement the high-level policy becomes low level, and the software is in charge of writing the iptables rules.

	\medskip
	If one changes mind and wants to use a different firewall instead of iptables, the original sentence does \emph{not} change: only the logic of the controller does. The same happens with SDN switches: the user specifies that a communication between two parts of the network is wanted, and the controller refines this decision into the low-level rules written on the switches. The concept of IBN and PBNM is therefore broader than forwarding: it is applicable to any context.
\end{notebox}
